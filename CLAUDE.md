# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

pnpm workspace; run from the repo root. README asks for Node 24 and pnpm 12.

- Install: `pnpm install`. The extension's `postinstall` runs `wxt prepare`, which generates `apps/extension/.wxt/`. `apps/extension/tsconfig.json` extends that generated file, so typecheck fails until install has run.
- Test: run each package on its own, `pnpm --filter @kiwi-search/core test` (or `@kiwi-search/extension`, `@kiwi-search/mcp`). The root `pnpm test` is `pnpm -r test` and also reaches `packages/experiments`, which is only a shell (empty `src/` and `test/`), so `vitest` exits 1 there with "No test files found"; that failure predates the block-list work.
- Single test file: `pnpm --filter @kiwi-search/core exec vitest run test/fusion.test.ts` (swap the package filter for `@kiwi-search/mcp` or `@kiwi-search/extension`). Narrow to one case with `-t "<test name>"`.
- Typecheck: `pnpm typecheck` (`tsc` per package; the extension runs `wxt prepare` first). There is no lint script or lint config, so typecheck is the only static check.
- Build: `pnpm build` (only extension and mcp define `build`). Chrome extension: `pnpm --filter @kiwi-search/extension build`, output in `apps/extension/.output/chrome-mv3`, loaded unpacked. Firefox: `build:firefox`. Dev server: `pnpm dev`. MCP server bundle: `pnpm --filter @kiwi-search/mcp build` → `packages/mcp/dist/index.js`.

## Architecture

Three workspace packages. The extension is the only place that touches a browser; `core` is pure logic it calls into. `docs/PLAN.md` has the design rationale and the list of known gaps. The Chinese docs for people are indexed in `README.md`: `docs/STATUS.md` (summary, verification matrix, decisions), `docs/ARCHITECTURE.md`, `docs/DEVELOPMENT.md`, `docs/BLOCKLISTS.md` and `docs/DECISION-PROVIDERS.md`; this file stays the place for implementation detail and what was and was not verified.

**`packages/core`: the search pipeline.** `runSearch` in `src/pipeline.ts` is the whole flow, for one `SearchMode` (`web`, `images`, `video`, `academic`, `zhihu`, `xiaohongshu`, `wechat`, `x`):
- pick usable sources for the mode (`usableSources` in `config.ts`) and query them in parallel, each with its own timeout. A browser source's timeout starts when it calls `onStart` (after queueing and rate limiting), not when it is enqueued. The per-source result count comes from `resultCount` (`perSourceCount`, `imageCount`, `videoCount`, `noteCount`).
- every finished source emits a partial `fused` event; with `softDeadlineMs` set (the new-tab page uses 6s, MCP does not) slow sources are left running and merged later like captcha-blocked ones (`late_results`, emitted after `done`, judged first when the judge is on). The summary is decided once, when the deadline passes: later results never start one. So if a summary is wanted and none of the sources in by then has any text, the deadline keeps waiting for the first source that does (found when a cold start left only DuckDuckGo in at 6 s, and the overview was lost for that search).
- **The decision model** (`decision.ts`, protocol in `docs/DECISION-PROVIDERS.md`) answers the small questions the search asks (is this a paper search? is that page filler?). It is a provider layer, not TypeSafe: `judge.provider` is `systemone` (default; a dedicated model behind `judge.endpoint`, which speaks System One's request/response: TypeSafe's Jev is only the preset, any service implementing the protocol can be pointed at, keyless if it runs on this machine), `llm` (only the user's chat model) or `none`. The dedicated model is the recommended one (about 0.9 s for the intent verdict against 2.9 s for a chat model, and one cheap request per result); the user's OpenAI-compatible chat model (`decisionLlm(config)`: the AI-overview model `config.llm` while `judge.llmShared`, else `judge.llm`) is the fallback, used when no dedicated model is set up, or when it refuses outright (`isHardFailure`: a 4xx other than 408/429, e.g. a 401 bad key or a 451 region block, or no connection; never a timeout, 429 or 5xx) and `judge.fallbackToLlm` is on. `resolveDecisionProvider(config)` says who would answer now; `decisionModelUsable` (= `judgeEnabled`) whether anyone can. Everything asks through `askDecision` and gets System One's shape back (`answers: {id: {noul|score}}`), so thresholds, hiding and routing are the same for every provider. The chat-model path sends the questions as one JSON chat request (`chatForJson`: JSON mode, and again without it when the provider answers 400/422; replies are clamped, a 0-100 probability is scaled, a skipped question is left out) and judges results ten per request, three requests at a time, instead of one per result; if the dedicated model refused every per-result request, the batch path takes over. Chat models are slower (the dev reasoning model: intent 1.7-5.8 s, twelve results 4.5 s), so the defaults are `intent.timeoutMs` 8 s and `judge.timeoutMs` 12 s (config migrations 3→4→5 widen the old 3 s / 6 s and rename `typesafe` to `systemone`), and the search waits past the soft deadline for a verdict still on its way (what it switches on is then late and merges in afterwards). The settings page tests a dedicated model with `kiwi:test-decision` (`handleDecisionTest` in `lib/llmTest.ts`). Checked live 2026-11-12: the dev chat model's verdicts match Jev's on 17 queries (杭州三日游攻略 xhs 0.97, 猫咪图片 images 0.99, 周杰伦 演唱会 video 0.95, weather/documentation ~0); the four cases dedicated / nothing configured / refused (wrong key) / refused with fallback off behave as above; the example server in the protocol document works unchanged.
- In the general (`web`) mode, when the decision model is on, `intent.ts` asks it about the query alone (academic? Zhihu? Xiaohongshu? WeChat? images? video? six Noul questions) while the general sources are already running. Routes at or above `intent.threshold` start their sources mid-search (`launch` in `pipeline.ts`), each in its own mode so it builds its own URL and shares its own cache, and join the same fusion; a `routed` event reports the verdict. No key, an error, `intent.timeoutMs` (3s) or a verdict that arrives after the soft deadline just leaves the general sources. Not used with explicit `sources` or in other modes. The `routed` event also carries `suggest` (`IntentSuggestion`: the best of academic / images / video at or above `intent.threshold`, `strong` when at or above `intent.switchThreshold` and `intent.autoSwitch`). The new-tab page decides what to do with it in `lib/suggestion.ts`: when `strong`, the search was typed (or the page opened with it) and no results are showing yet, it moves to that tab by itself (`history.replaceState`) and says so with a way back ("仍看网页结果"); otherwise, or after a Back or a reload, it only offers the tab in one line. Without a usable decision model none of this runs and nothing says so (it is a choice the settings page explains); when one is set and the verdict fails, the `routed` event's `error` becomes `SearchState.intentError` and the status line says so, in one line when the filter failed for the same reason (`decisionModelNotes` and `explainServiceError` in `lib/results.ts`, which put HTTP 451 / 401 / 429 into words). Checked live on 2026-11-12 with the real model (`api.typesafe.ai` reachable from Node): platform-style queries score 0.8-0.98 (杭州三日游攻略: zhihu 0.96, xiaohongshu 0.96, wechat 0.82), weather, documentation and a random token score under 0.4, so 0.6 behaves sensibly; the 0.85 auto-switch only fired for 猫咪图片 (images 0.99) and 周杰伦 演唱会 (video 0.87). From the browser the same endpoint answered 3 requests and then HTTP 451 \"not available in your region\" for the next 7, while curl got 10 of 10: the browser's connections left through another proxy exit, so a proxy needs a direct or supported-region rule for `api.typesafe.ai` (one more reason the decision model is not tied to TypeSafe). The 0.6 and 0.85 thresholds are still a first guess, from about 17 queries.
- Smart academic search (`academic.ts`, academic mode only, not with explicit `sources`, needs `config.academic.smart` and a usable `config.llm`): while the normal sources run, the user's own model reads the query and returns JSON (`intent`, `keywords`, search text per academic API source, up to `academic.landmarks` paper titles); `parsePlan` clamps it (the reply is data, never instructions). Each named title is looked up in OpenAlex (Crossref when OpenAlex is off) by `verifyPapers`; a title the index doesn't have is thrown away, so the model's memory alone never puts a paper on the page, and with neither index on nothing is shown. The verified papers go first into the fusion (so their rank counts even if a source also returned them), then come second-round lists: the model's search text on each API source whose text differs from the typed query, and a most-cited pass (`cited_by_count:desc`) on OpenAlex. Browser sources are not queried a second time (a tab to queue, a captcha to risk). The whole plan is bounded by `academic.timeoutMs` (12s) and the pipeline waits for it even past the soft deadline, so its papers are in the first full list; a model error or timeout just leaves the plain search. Events: `academic_plan` (`plan`, `landmarks`, or `error`); `PipelineResult` carries `plan` and `landmarks`, and MCP `search` reports both. The page shows the intent line, the search text folded, and a "核心文献" block (`entrypoints/newtab/AcademicPlan.tsx`, `pickLandmarks` in `lib/results.ts` matches them in the fused list by DOI or whole title) above the list, which no longer repeats them.
- URL-normalized dedupe and RRF fusion (`fusion.ts`): DOI (also from publisher URLs) and arXiv IDs, papers by an equal `meta.doi` (PubMed and Europe PMC link their own pages, so their URL keys differ from a `doi.org` one) or by long title + compatible year, images by image file. `foldReprints` (called by `fuse` and `mergeLateHits`) folds the same article posted on several sites into one result with `reprints`: same title (site suffix like `_CSDN博客` stripped, at least 12 characters), different sites, AND the engines' texts overlap (two-character pieces, at least half of the shorter one); it keeps the copy that is not on a republishing site (`REPRINT_HOSTS`), then the earliest date, then the best rank. Papers, images, video and notes are never folded. Which copy is the original is a guess, so the page says only "同一篇还出现在 …". Then `applyDomainRules` (blocked/boosted domains, no key needed).
- **Block lists** (`blocklist.ts`, no key needed): `config.judge.blocklists` holds `recommended` (ids from `RECOMMENDED_BLOCKLISTS`; all off by default, because a subscription is a request to a third-party host), `subscriptions` (the user's own `{id, name, url, enabled}`; https only, plain http only for localhost: `isSubscriptionUrl`) and `custom` (the user's own rules as text). `parseBlocklist` reads one syntax per line: plain domains (`example.com`, `*.example.com`, leading-dot `.example.com`, `example.com/path`, wildcard hosts `foo.blogspot.*`, IPv4), hosts-file lines, uBlock Origin / Adblock Plus network filters (`||x^`, `||x/path^`, `|https://x/y`; options `$doc`/`$all`/`$document`/`$important` and the `reason="…"` annotation the AI uBlock Blacklist puts on every line are accepted, any other option such as `$script` or `$third-party` makes the rule unsupported), uBlacklist match patterns (`*://*.x/*` is the site and its subdomains, `*://x/*` is that one host, `*://x/blog/*` a section), `/regex/` lines, and exceptions (`@@…` and `@…`). Page-element filters (`##`, `#@#`…), comments, a leading `---` header block and anything else that cannot be matched against a search result are skipped and counted (`stats.cosmetic`, `stats.unsupported` with a few `examples`). `www.` is not told apart from the bare domain. A regex is kept only if it names a site (`example\.com`), has no `(a+)+`-style nested quantifier or backreference, is at most 400 chars and does not match two of three unrelated probe URLs; this is a heuristic, not a proof, and it also drops URL-shape regexes like `/.*\/(.*)(s|q)=.*/` that would hide ordinary pages. The check applies only to regexes someone wrote (a list's `/…/` line, a `|` filter), not to the ones built from a validated host. The parsed `BlockRules` (`block` and `allow`, each `sites` / `hosts` / `patterns`) are plain JSON; `compileBlocklist` indexes them (a `Set` walked up the host's labels for sites and hosts, a linear scan of regexes against the first 2048 chars of the URL, one memo per search, the index itself kept per rules object in a `WeakMap`). `runSearch` starts `loadBlocklist(config, env)` beside the sources (never awaited before they start, never rejects) and every list of results, partial `fused` events included, goes through `applyDomainRules(results, judge, lists)`; before this the partial events skipped domain rules, so blocked results showed until the soft deadline. What hides a result, in order: the user's own `blockedDomains` (no list name); otherwise an exception in any list, or the user boosting the site, keeps it; otherwise the first list that matches (`HiddenReason` is `{ reason: 'blocked', list?: name }`, which the page and the MCP `hidden` entries show). `Env.loadBlocklists(settings)` supplies the subscribed lists' parsed rules; the user's `custom` text is parsed in core (`parseBlocklistCached`). Checked on 2026-11-12 against the real lists (Content Farm Terminator 20.5k rules incl. 3.3k regexes and wildcard hosts, 4 lines unusable; AI uBlock Blacklist 2.6k; BadWebsiteBlocklist 418 incl. 204 section rules; eallion's uBlacklist 15.6k, 1.7k of its lines being cosmetic filters): `packages/core/test/fixtures/blocklist-excerpts.txt` is verbatim lines of them; 100 non-matching results against all four lists took about 39 ms, once per URL. eallion's compilation is deliberately **not** in the catalog: it also carries its author's taste (all of baidu.com, csdn.net, juejin.cn, amazon.com and sohu.com are in it); the three that are in hide none of 62 popular sites' home pages.
- `judge.ts` (through the decision model; TypeSafe: one request per result): relevance Score, junk Noul, one Noul per user rule. It orders results and flags some as `hidden`; when active it replaces `rerank.ts`. It also checks fetched page text for prompt injection before summarizing.
- optional summary with `[n]` citations (`summarize.ts`, page text from `content.ts`), only from non-hidden results; community posts (Zhihu, WeChat, Xiaohongshu) are labelled `Platform:` in the prompt and, when the sources mix platforms and ordinary pages, the model is asked to say what each platform says and how they differ (only differences the sources show); images, video and Xiaohongshu notes get no summary and no judging, Zhihu answers do (`modeHasText` in `types.ts` decides). `content.ts` never fetches zhihu/xiaohongshu/rednote pages (a plain fetch hits the login wall); their own excerpt is used. Academic mode uses a literature-overview prompt.
- `Env.cache` (`cache.ts`, 5 min TTL, shared by the new-tab page and the MCP bridge) caches hits per mode/source/count/query.
Progress is emitted as `PipelineEvent`s through `onEvent`; the new-tab UI and the MCP bridge both consume that stream. Core never calls `browser.*` directly. The caller passes an `Env` with `fetch`, `cache` and, for browser engines, `runBrowserEngine`. The renderer settings travel inside `BrowserRunOptions`, so one search uses one config snapshot.

Sources are unified as `SearchSource` and registered in `src/sources/index.ts` (`SOURCES`). Each declares `modes`, `requiresKey` and, if needed, `requiresBaseUrl`/`requiresBrowser`:
- Browser engines (`google`, `bing`, `baidu`, `duckduckgo`, `scholar`, `baiduxueshu`, `cnki`, `wos`, `yandex`, `youtube`, `bilibili`, `zhihu`, `xiaohongshu`, `rednote`, `sogou`, `weixin`, `x`) are `BrowserEngine` objects in `src/engines/*.ts`: `buildUrl(query, count, mode)`, `matches`, `readySelector` (a selector list covering all modes), `blockedSelector`, `isBlockedUrl`, `extract(doc, pageUrl, mode)`, and an optional `resolve` for unwrapping redirect links. `makeBrowserSource` in `engines/shared.ts` wraps them as sources. Bing serves web and images through the same worker tab and queue. The YouTube engine reads the inline `ytInitialData` JSON from the page's scripts (so its `readySelector` is just `body`) instead of the custom-element DOM; the Bilibili engine reads the rendered `.bili-video-card` DOM. Zhihu and Xiaohongshu only work in a browser the user is signed in to. Xiaohongshu has two sources, `xiaohongshu` (mainland) and `rednote` (international), with separate domains and logins but the same note ids (normalized to `xhs:<id>` in `url.ts`, so both merge); `rednote` is on by default and the mainland site is opt-in. Note links keep `xsec_token`/`xsec_source`, which the site needs to open a note. Zhihu keeps its author in `meta.author`, not `meta.authors`, because `authors` marks a result as a paper for de-duplication and would merge different answers to one question. The Sogou WeChat engine (`weixin`, mode `wechat`) finds WeChat official-account articles; it returns Sogou's own redirect links (`/link?url=…`), which, opened without a Referer, land on the article at mp.weixin.qq.com (checked), so they are kept as they are and `host` is set to `mp.weixin.qq.com`. The publish time comes from the text of the `timeConvert('<unix seconds>')` script, which is never run. `sogou` (Sogou web search, off by default) also keeps redirect links and takes the site from a card's `data-url`. Neither needs a login. X (`x`, mode `x`) works only in a browser signed in to X (signed out, a search redirects to `/i/jf/onboarding/web`, which `isBlockedUrl` recognizes). It is a tab of its own and never a route of the general search; its tweets are not judged or summarized (`modeHasText('x')` is false). X polices automated use of an account, so the engine sets `BrowserEngine.minIntervalMs` (10 s), which `tabRenderer.ts` applies on top of `renderer.minIntervalMs` between request *starts*. X renders a virtualized list and renders nothing new while the worker window is minimized (page visibility `hidden`; scrolling the worker page changed nothing), so a search returns only the 4–6 tweets of the first render, and getting more would mean bringing the window forward. The engine skips promoted tweets (a bare `Ad` label), takes a quote tweet's own text instead of the quoted one's, uses the title and preview of an X Article when a post has no tweet text, and reads the counts from the `aria-label` of the action row.
- API sources (`brave`, `exa`, `deepseek`, `openalex`, `crossref`, `arxiv`, `openverse`, `pubmed`, `europepmc`, `dblp`, `searxng`) live in `src/sources/*.ts` and call HTTP through `env.fetch`. Openverse is anonymous-limited (20 results per page, 200 requests a day).
- Six more `academic`-mode sources, all keyless and all opt-in except PubMed (`DEFAULT_CONFIG`): `pubmed` (on by default), `europepmc`, `dblp`, `baiduxueshu`, `cnki`, `wos` (off). The three browser ones return only what the user's own browser session can see; none ships a key or account.
  - `pubmed`: `esearch` (JSON, relevance order) then one `efetch` (XML, the only format with abstracts), so two requests a search against NCBI's 3 a second without a key; a user-supplied `apiKey` is sent as `api_key` on both. Over the limit NCBI answers 200 with an `error` field, which is thrown. Links `pubmed.ncbi.nlm.nih.gov/<pmid>/`; skips queries with no Latin letter. The XML parser needs lower-case tag selectors (`pubmedarticle`) and reads the article's own DOI from `ELocationID` / the direct `ArticleIdList` because the reference list holds hundreds of other IDs.
  - `europepmc`: REST `search`, `resultType=core`. A `MED` record links PubMed (same URL as the PubMed source, so the two fuse by key); others link `europepmc.org/article/<source>/<id>`. Preprints have no `journalInfo` (the publisher stands as venue) and abstracts carry markup, which is stripped.
  - `dblp`: no abstracts; the snippet is the byline. dblp.org sits behind an Anubis proof-of-work bot check that answers HTTP 202 HTML instead of JSON to some clients (it did, from every host and user agent tried on the capturing machine); the source throws "bot check" rather than returning nothing. Links the record's `ee` (DOI / arXiv / publisher link, so it fuses) or DBLP's own page.
  - `baiduxueshu`: `xueshu.baidu.com/s?wd=` settles on the single-page app at `/ndscholar/browse/search` (both are in `matches`); cards are `div.paper-wrap.result`, links are Baidu Scholar's own detail pages. A cold headless profile got "百度安全验证" at the *same* address, so `blockedSelector` keys on the captcha library's own script/link files; opening the site's home page first got real results.
  - `cnki`: kns8s search. A cold headless profile was redirected to `/verify/home?captchaType=blockPuzzle` (slider captcha), which `isBlockedUrl` recognizes. The result-table parser is from memory, unverified against a real page.
  - `wos`: with no institutional IP or login, the app sends the browser to `access.clarivate.com/login` (another host, so it is in `matches`; `isBlockedUrl` recognizes the host and the source reports `blocked` instead of timing out). The search address and the `app-record` / `data-ta` parser are from memory, unverified (they need an account).
- Adding a source touches five places: the hand-written `SourceId` union in `types.ts`, the `SOURCES` registry (typed as `Record<SourceId, …>`, so TypeScript flags a gap), `SOURCE_LABELS` in the extension's `lib/sourceMeta.ts` and `SOURCE_MARKS` in `lib/sourceMarks.ts` (both also a `Record<SourceId, …>`; its logo goes into `assets/engine-logos`, see below), and `DEFAULT_CONFIG.sources` in `config.ts`. That last field is `Partial`, so a missing entry is not flagged; the source then silently defaults to disabled.
- Config has a `version` (`CONFIG_VERSION`); put rewrites of stored configs in `MIGRATIONS` in `config.ts`. `baidu` is off by default and last in `BROWSER_ENGINES` (the options page groups sources by content type in `lib/sourceCatalog.ts`, in the order of that file): its result page mixes in widgets (translate cards, recommendation lists, hosts like `nourl.ubs.baidu.com`) that the parser reads as results. Migration 2→3 switched it off in stored configs, and switching it on in the options page opens a confirmation dialog (`confirm` in its `SOURCE_INFO` entry). New fields only need defaults.

**`apps/extension`: WXT + React, Manifest V3.** `entrypoints/` holds the entry points.
- `background.ts` is the service worker and runs the pipeline. The new-tab page opens a `runtime.connect({ name: 'search' })` port, sends a `search` request (`query`, `mode`), and receives streamed `PortMessage`s. The same file registers the omnibox keyword, a declarativeNetRequest redirect from `https://s.kiwi.moe/s?…` to `newtab.html`, the `kiwi:*` runtime messages, and the MCP bridge with its reconnect alarm. The options page only opens on first install. It is declared `open_in_tab` (the meta tag `manifest.open_in_tab` in `entrypoints/options/index.html`; WXT's default is `false`), so "Extension options" opens a full tab instead of the small embedded view inside chrome://extensions.
- Browser engines run in `lib/tabRenderer.ts`. Each `SourceId` has its own serial queue and a minimum interval between requests (`renderer.minIntervalMs`). Each engine gets one persistent, muted worker tab. All worker tabs live in one window of their own, in one grey tab group titled `Kiwi Search` (not collapsed: it is the only group in that window, and collapsing a group that holds the active tab is an edge case; `tabs.group` must be given `createProperties.windowId`, because a new group otherwise goes into the *current* window, which drags the worker tab into the user's window and closes the emptied worker window), and that window is minimized right after it is created, so search pages never appear in the window the user is working in (`windows.create({ state: 'minimized' })` alone is ignored by macOS Chromium, hence the explicit `windows.update`). The window is recreated if the user closes it. Worker state is stored in `chrome.storage.session` under `kiwiRenderer`.
- `entrypoints/engines.content.ts` is injected into engine result pages (its `matches` come from `BROWSER_ENGINES`). A page handshakes with `kiwi:worker?` and gets the requested `count` and `mode`, so only registered worker tabs do anything. It watches DOM mutations (debounced), waits for `readySelector`, and extracts: it returns at once with `count` results, otherwise after the page has been quiet for 600ms, and at the 12s timeout with whatever is there. On a captcha or block page it sends `kiwi:blocked` with a `reason`: `login` when the engine's `isLoginUrl`/`loginSelector` match (a site the browser isn't signed in to: Zhihu, Xiaohongshu, X), otherwise `captcha` (`isBlockedUrl`/`blockedSelector`; use `':not(*)'` when no captcha markup is known). The pipeline then marks that source `blocked` (`source_blocked` carries the reason, `sourceStats[].blockedReason` keeps it) and extends its timeout to 120s. The new-tab page offers one action per reason ("去登录" / "去验证"), and only a captcha may bring the window forward by itself. Two more ways a worker page fails fast instead of waiting out the timeout: an engine's `refusedPattern` matching the page text (the site refuses outright; the content script sends `kiwi:refused`, e.g. Zhihu's risk-control JSON `code 40362`), and a page that finished loading but whose content script never said hello within 4s (`HANDSHAKE_GRACE_MS` in `tabRenderer.ts`: the browser's own error page, an HTTP 403 that keeps the requested address, a redirect to a page the engine doesn't read). Both reject the request, which `sourceStatus` records as "上次出错" with the reason. Checked in a fresh, signed-out headless Chromium: Zhihu answered the search URL with that JSON (0.8s to fail, was 13.8s) and X with Chrome's 403 page (5.0s, was 15s); a real signed-out Zhihu/X login wall was NOT seen there, so `loginSelector`/`isLoginUrl` for those are still guesses. The new-tab page shows one quiet line with a "verify" link; the worker window is brought forward only when the user clicks it (`kiwi:focus-worker`), or by itself if `renderer.focusOnCaptcha` is on. That is off by default (config migration 1→2 turned off the old saved default), and the window is minimized again once the extraction arrives.
- The new-tab page: `lib/useSearchSession.ts` owns the port, keepalive and the built-in-model summary; `lib/searchState.ts` is the pure reducer over `PipelineEvent`s; `lib/results.ts` and `lib/justify.ts` are pure helpers (`modeHasOverview` there mirrors core's `modeHasText`; importing core into the page bundle would pull in the parsers). Components are in `entrypoints/newtab/`. In a general search the community posts that the intent routes pulled in leave the list and gather in a "各平台怎么说" block after the first three results (`splitPlatforms`, at least two posts, at most six and three per platform; `PlatformStrip.tsx`) with a link into each platform's own tab; the platform tabs (知乎, 小红书, 公众号, X) are folded under one "社区" tab (`ModeTabs.tsx`, `COMMUNITY_MODES`). The page shows which engines returned a result only as small marks after the site name, and only when two or more distinct engines did (`lib/sourceMarks.ts` orders and dedupes them by rank, `entrypoints/newtab/SourceMarks.tsx` renders them: each logo on a small round chip, the chips stacked tight with the best-ranked on top and fanning out with a gap on hover or focus; none in the folded hidden section). The logos are real brand logos, never drawn here: files in `apps/extension/assets/engine-logos/` (from SVG Logos and Simple Icons, both CC0, from Font Awesome Free Brands (CC BY 4.0, the Yandex Y) or the brand's own site icon), with their origin and licence in `logos.json` and `NOTICE.md` (a test insists on both). `scripts/gen-source-icons.mjs` turns them into data URIs in `lib/sourceIcons.ts` (`dark` is a variant for the dark page, `invertInDark` a black raster that is inverted there), so nothing is fetched; each mark is a `<picture>`/`<img>`. A new engine needs its logo file and a `logos.json` entry; if no collection carries it, take the brand's own site icon, and never invent a letter badge. Beyond that, a captcha prompt is the only place a source is named. Site icons in the result headers come from the background (`lib/faviconService.ts`, message `kiwi:favicon`; `lib/favicon.ts` is the pure part): Chrome's `_favicon` API is *not* enough on its own, because it only serves icons the browser already holds from visits and bookmarks and answers every other site with the same placeholder globe (checked: GitHub, Stack Overflow, Wikipedia and a made-up host returned byte-identical 646-byte images). So the order is the browser's own icon (the placeholder is recognized by comparing with the answer for a made-up host), then the site's `/favicon.ico` and the `<link rel="icon">` of its home page (no cookies, no referrer, public host names only, image type decided from the bytes because many sites answer a missing icon with a 200 HTML page), then a letter badge. Results are cached per host in `storage.local` (`favicon:<host>`, 7 days for hits, 6 hours for misses, pruned to 400 entries), and at most 4 site requests run at once. The cost of this is that a site you have never visited receives one icon request (and one home-page request when it has no `/favicon.ico`) when it shows up in results; no third-party icon service sees your results. The URL is `newtab.html?q=…&m=images|video|academic|zhihu|xiaohongshu|wechat|x`, and new searches use `pushState`.
- Settings are in `chrome.storage.local` under `config` and `bridge` (`lib/settings.ts`); `onboarding` remembers that the first-run guide was finished, and `sourceStatus` (`lib/sourceStatus.ts`, pure part in `lib/sourceHealth.ts`) keeps what the last search that touched each source found (ok / empty / login / captcha / error), written from the pipeline events by the background and the MCP bridge. The options page (`entrypoints/options/`) autosaves (`useAutosave.ts`), groups sources by content type (`lib/sourceCatalog.ts`, typed over `SourceId`) and shows each source's status from `sourceStatus` (`lib/sourceView.ts`); the "测试连接" button sends `kiwi:test-llm` to the background (`lib/llmTest.ts`). `loadConfig` runs `migrateConfig`, then deep-merges over `DEFAULT_CONFIG`, so new config fields need defaults in `config.ts`.
- Block-list subscriptions live in the extension: `lib/blocklistService.ts` (storage and fetching) over `lib/blocklistState.ts` (pure: what is due, how a download is read, the status wording). `storage.local` holds `blocklistMeta` (small, per list: address, `fetchedAt`, `attemptedAt`, `etag`, rule counts, `error`, `updatingSince`; the settings page watches it) and `blocklist:<id>` (the parsed rules, large: about 630 KB for the 20.5k-rule list). The background refreshes a list when the worker starts (a no-op unless one is due), on an alarm every 6 hours (created only if absent: creating a named alarm again restarts it, and the worker restarts more often than that), when `activeSubscriptions` changes in a stored config (switching one on, adding one, changing an address; editing the custom text does not) and on `kiwi:blocklist-refresh` (the settings page's "立即更新", forced). A list is due after 24 h, or 1 h after a failure; a download sends no cookies and no referrer, uses the kept `ETag` for a 304, is capped at 12 MB and 30 s, and a list that parses to zero rules is an error. A failed refresh keeps the rules from before (the status line says so). Switching a recommended list off or removing a subscription deletes its stored rules (`prune`); the parsed rules of a list are kept in memory per worker so a search does not parse megabytes of JSON. `makeEnv` in `background.ts` passes `loadBlocklists`, so the MCP bridge hides the same results. The panel is `entrypoints/options/BlocklistsPanel.tsx` (inside the "屏蔽与偏好" section, reusing the source-row styles): recommended lists with a switch and a status line, subscriptions by address, the custom text with a live count of what was understood, and a syntax cheat sheet. Reset to defaults clears all of it. Checked on 2026-11-12 in headless Chromium 156 with a throwaway profile (`--load-extension`, lists served from localhost): setting the config in storage made the worker download and store the real 20.5k-rule list by itself, `kiwi:blocklist-refresh` answered, the panel rendered the status, and a real web search folded blog.csdn.net and github.com results as "命中屏蔽列表「…」" while the other six stayed. Later the same day, with the user's own Exa key as the only enabled source (a real Exa search, 10 results, in a throwaway headless Chromium; harness kept outside the repo in `~/.kiwi-search/e2e/`), 24 checks passed: a subscription served from localhost is downloaded by the worker by itself and folds the right Exa results with the list's name; an `@@` exception and the user's own rules (label 自定义规则) work; a forced refresh sends the kept ETag and a 304 keeps the rules and the download time; an HTTP 500 and a 200 page with no rules are reported as errors while the old rules keep hiding results; a changed list replaces the rules; switching a list off hides nothing and removing it (even one already switched off) forgets its stored rules; the three recommended lists download from their real addresses through the extension (20,547 / 2,636 / 418 rules) and hide nothing in an ordinary search. Not seen live: the 6-hour alarm firing, Firefox.

**`packages/mcp`: stdio MCP server that forwards to the browser.** `src/index.ts` reads or creates the pairing token at `~/.kiwi-search/token` (`KIWI_HOME` overrides the directory). Tools are defined in `src/server.ts` (`search` and `answer` take `mode`).
- `BridgeSession` (`src/session.ts`) owns the link. The first MCP process to start binds `127.0.0.1:17345` (`KIWI_PORT`) and becomes the `BridgeHub`. It accepts the extension at `/extension`, which must present the token and a `chrome-extension://` origin, and relay clients at `/mcp`.
- Any later MCP process gets `EADDRINUSE` and becomes a `RelayClient` that talks to the existing hub. One browser connection therefore serves several MCP clients. The hub remaps request IDs (`routeId`) in `src/bridge.ts`. If the hub process exits, the relays race to bind the port again, so one of them becomes the new hub.
- The extension side is `apps/extension/lib/bridge.ts`. It runs each MCP request through the same `runSearch`, so MCP calls share the UI's queues, rate limits, cache and worker tabs. Hidden (filtered) results are left out of the tool text and listed under `structuredContent.hidden`.
- `answer` fails when the summary provider is `chrome-builtin`, because that model only runs in the new-tab page.
