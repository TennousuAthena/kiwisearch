# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

pnpm workspace; run from the repo root. README asks for Node 24 and pnpm 12.

- Install: `pnpm install`. The extension's `postinstall` runs `wxt prepare`, which generates `apps/extension/.wxt/`. `apps/extension/tsconfig.json` extends that generated file, so typecheck fails until install has run.
- Test all packages: `pnpm test` (runs `vitest run` in core, extension, and mcp).
- Single test file: `pnpm --filter @kiwi-search/core exec vitest run test/fusion.test.ts` (swap the package filter for `@kiwi-search/mcp` or `@kiwi-search/extension`). Narrow to one case with `-t "<test name>"`.
- Typecheck: `pnpm typecheck` (`tsc` per package; the extension runs `wxt prepare` first). There is no lint script or lint config, so typecheck is the only static check.
- Build: `pnpm build` (only extension and mcp define `build`). Chrome extension: `pnpm --filter @kiwi-search/extension build`, output in `apps/extension/.output/chrome-mv3`, loaded unpacked. Firefox: `build:firefox`. Dev server: `pnpm dev`. MCP server bundle: `pnpm --filter @kiwi-search/mcp build` → `packages/mcp/dist/index.js`.

## Architecture

Three workspace packages. The extension is the only place that touches a browser; `core` is pure logic it calls into. `docs/PLAN.md` has the design rationale and the list of known gaps.

**`packages/core`: the search pipeline.** `runSearch` in `src/pipeline.ts` is the whole flow, for one `SearchMode` (`web`, `images`, `video`, `academic`, `zhihu`, `xiaohongshu`, `wechat`, `x`):
- pick usable sources for the mode (`usableSources` in `config.ts`) and query them in parallel, each with its own timeout. A browser source's timeout starts when it calls `onStart` (after queueing and rate limiting), not when it is enqueued. The per-source result count comes from `resultCount` (`perSourceCount`, `imageCount`, `videoCount`, `noteCount`).
- every finished source emits a partial `fused` event; with `softDeadlineMs` set (the new-tab page uses 6s, MCP does not) slow sources are left running and merged later like captcha-blocked ones (`late_results`, emitted after `done`, judged first when the judge is on). The summary is decided once, when the deadline passes: later results never start one. So if a summary is wanted and none of the sources in by then has any text, the deadline keeps waiting for the first source that does (found when a cold start left only DuckDuckGo in at 6 s, and the overview was lost for that search).
- In the general (`web`) mode, when the judge is on, `intent.ts` asks Jev about the query alone (academic? Zhihu? Xiaohongshu? WeChat? images? video? one System One request, six Noul questions) while the general sources are already running. Routes at or above `intent.threshold` start their sources mid-search (`launch` in `pipeline.ts`), each in its own mode so it builds its own URL and shares its own cache, and join the same fusion; a `routed` event reports the verdict. No key, an error, `intent.timeoutMs` (3s) or a verdict that arrives after the soft deadline just leaves the general sources. Not used with explicit `sources` or in other modes. The `routed` event also carries `suggest` (`IntentSuggestion`: the best of academic / images / video at or above `intent.threshold`, `strong` when at or above `intent.switchThreshold` and `intent.autoSwitch`). The new-tab page decides what to do with it in `lib/suggestion.ts`: when `strong`, the search was typed (or the page opened with it) and no results are showing yet, it moves to that tab by itself (`history.replaceState`) and says so with a way back ("仍看网页结果"); otherwise, or after a Back or a reload, it only offers the tab in one line. The 0.6 and 0.85 thresholds are uncalibrated starting values.
- Smart academic search (`academic.ts`, academic mode only, not with explicit `sources`, needs `config.academic.smart` and a usable `config.llm`): while the normal sources run, the user's own model reads the query and returns JSON (`intent`, `keywords`, search text per academic API source, up to `academic.landmarks` paper titles); `parsePlan` clamps it (the reply is data, never instructions). Each named title is looked up in OpenAlex (Crossref when OpenAlex is off) by `verifyPapers`; a title the index doesn't have is thrown away, so the model's memory alone never puts a paper on the page, and with neither index on nothing is shown. The verified papers go first into the fusion (so their rank counts even if a source also returned them), then come second-round lists: the model's search text on each API source whose text differs from the typed query, and a most-cited pass (`cited_by_count:desc`) on OpenAlex. Browser sources are not queried a second time (a tab to queue, a captcha to risk). The whole plan is bounded by `academic.timeoutMs` (12s) and the pipeline waits for it even past the soft deadline, so its papers are in the first full list; a model error or timeout just leaves the plain search. Events: `academic_plan` (`plan`, `landmarks`, or `error`); `PipelineResult` carries `plan` and `landmarks`, and MCP `search` reports both. The page shows the intent line, the search text folded, and a "核心文献" block (`entrypoints/newtab/AcademicPlan.tsx`, `pickLandmarks` in `lib/results.ts` matches them in the fused list by DOI or whole title) above the list, which no longer repeats them.
- URL-normalized dedupe and RRF fusion (`fusion.ts`): DOI (also from publisher URLs) and arXiv IDs, papers by long title + compatible year, images by image file. `foldReprints` (called by `fuse` and `mergeLateHits`) folds the same article posted on several sites into one result with `reprints`: same title (site suffix like `_CSDN博客` stripped, at least 12 characters), different sites, AND the engines' texts overlap (two-character pieces, at least half of the shorter one); it keeps the copy that is not on a republishing site (`REPRINT_HOSTS`), then the earliest date, then the best rank. Papers, images, video and notes are never folded. Which copy is the original is a guess, so the page says only "同一篇还出现在 …". Then `applyDomainRules` (blocked/boosted domains, no key needed).
- `judge.ts` (TypeSafe System One / Jev, one request per result): relevance Score, junk Noul, one Noul per user rule. It orders results and flags some as `hidden`; when active it replaces `rerank.ts`. It also checks fetched page text for prompt injection before summarizing.
- optional summary with `[n]` citations (`summarize.ts`, page text from `content.ts`), only from non-hidden results; community posts (Zhihu, WeChat, Xiaohongshu) are labelled `Platform:` in the prompt and, when the sources mix platforms and ordinary pages, the model is asked to say what each platform says and how they differ (only differences the sources show); images, video and Xiaohongshu notes get no summary and no judging, Zhihu answers do (`modeHasText` in `types.ts` decides). `content.ts` never fetches zhihu/xiaohongshu/rednote pages (a plain fetch hits the login wall); their own excerpt is used. Academic mode uses a literature-overview prompt.
- `Env.cache` (`cache.ts`, 5 min TTL, shared by the new-tab page and the MCP bridge) caches hits per mode/source/count/query.
Progress is emitted as `PipelineEvent`s through `onEvent`; the new-tab UI and the MCP bridge both consume that stream. Core never calls `browser.*` directly. The caller passes an `Env` with `fetch`, `cache` and, for browser engines, `runBrowserEngine`. The renderer settings travel inside `BrowserRunOptions`, so one search uses one config snapshot.

Sources are unified as `SearchSource` and registered in `src/sources/index.ts` (`SOURCES`). Each declares `modes`, `requiresKey` and, if needed, `requiresBaseUrl`/`requiresBrowser`:
- Browser engines (`google`, `bing`, `baidu`, `duckduckgo`, `scholar`, `yandex`, `youtube`, `bilibili`, `zhihu`, `xiaohongshu`, `rednote`, `sogou`, `weixin`, `x`) are `BrowserEngine` objects in `src/engines/*.ts`: `buildUrl(query, count, mode)`, `matches`, `readySelector` (a selector list covering all modes), `blockedSelector`, `isBlockedUrl`, `extract(doc, pageUrl, mode)`, and an optional `resolve` for unwrapping redirect links. `makeBrowserSource` in `engines/shared.ts` wraps them as sources. Bing serves web and images through the same worker tab and queue. The YouTube engine reads the inline `ytInitialData` JSON from the page's scripts (so its `readySelector` is just `body`) instead of the custom-element DOM; the Bilibili engine reads the rendered `.bili-video-card` DOM. Zhihu and Xiaohongshu only work in a browser the user is signed in to. Xiaohongshu has two sources, `xiaohongshu` (mainland) and `rednote` (international), with separate domains and logins but the same note ids (normalized to `xhs:<id>` in `url.ts`, so both merge); `rednote` is on by default and the mainland site is opt-in. Note links keep `xsec_token`/`xsec_source`, which the site needs to open a note. Zhihu keeps its author in `meta.author`, not `meta.authors`, because `authors` marks a result as a paper for de-duplication and would merge different answers to one question. The Sogou WeChat engine (`weixin`, mode `wechat`) finds WeChat official-account articles; it returns Sogou's own redirect links (`/link?url=…`), which, opened without a Referer, land on the article at mp.weixin.qq.com (checked), so they are kept as they are and `host` is set to `mp.weixin.qq.com`. The publish time comes from the text of the `timeConvert('<unix seconds>')` script, which is never run. `sogou` (Sogou web search, off by default) also keeps redirect links and takes the site from a card's `data-url`. Neither needs a login. X (`x`, mode `x`) works only in a browser signed in to X (signed out, a search redirects to `/i/jf/onboarding/web`, which `isBlockedUrl` recognizes). It is a tab of its own and never a route of the general search; its tweets are not judged or summarized (`modeHasText('x')` is false). X polices automated use of an account, so the engine sets `BrowserEngine.minIntervalMs` (10 s), which `tabRenderer.ts` applies on top of `renderer.minIntervalMs` between request *starts*. X renders a virtualized list and renders nothing new while the worker window is minimized (page visibility `hidden`; scrolling the worker page changed nothing), so a search returns only the 4–6 tweets of the first render, and getting more would mean bringing the window forward. The engine skips promoted tweets (a bare `Ad` label), takes a quote tweet's own text instead of the quoted one's, uses the title and preview of an X Article when a post has no tweet text, and reads the counts from the `aria-label` of the action row.
- API sources (`brave`, `exa`, `deepseek`, `openalex`, `crossref`, `arxiv`, `openverse`, `searxng`) live in `src/sources/*.ts` and call HTTP through `env.fetch`. Openverse is anonymous-limited (20 results per page, 200 requests a day).
- Adding a source touches five places: the hand-written `SourceId` union in `types.ts`, the `SOURCES` registry (typed as `Record<SourceId, …>`, so TypeScript flags a gap), `SOURCE_LABELS` in the extension's `lib/sourceMeta.ts` and `SOURCE_MARKS` in `lib/sourceMarks.ts` (both also a `Record<SourceId, …>`; a new brand glyph goes into the generator's table), and `DEFAULT_CONFIG.sources` in `config.ts`. That last field is `Partial`, so a missing entry is not flagged; the source then silently defaults to disabled.
- Config has a `version` (`CONFIG_VERSION`); put rewrites of stored configs in `MIGRATIONS` in `config.ts`. `baidu` is off by default and last in `BROWSER_ENGINES` (the options page groups sources by content type in `lib/sourceCatalog.ts`, in the order of that file): its result page mixes in widgets (translate cards, recommendation lists, hosts like `nourl.ubs.baidu.com`) that the parser reads as results. Migration 2→3 switched it off in stored configs, and switching it on in the options page opens a confirmation dialog (`confirm` in its `SOURCE_INFO` entry). New fields only need defaults.

**`apps/extension`: WXT + React, Manifest V3.** `entrypoints/` holds the entry points.
- `background.ts` is the service worker and runs the pipeline. The new-tab page opens a `runtime.connect({ name: 'search' })` port, sends a `search` request (`query`, `mode`), and receives streamed `PortMessage`s. The same file registers the omnibox keyword, a declarativeNetRequest redirect from `https://s.kiwi.moe/s?…` to `newtab.html`, the `kiwi:*` runtime messages, and the MCP bridge with its reconnect alarm. The options page only opens on first install.
- Browser engines run in `lib/tabRenderer.ts`. Each `SourceId` has its own serial queue and a minimum interval between requests (`renderer.minIntervalMs`). Each engine gets one persistent, muted worker tab. All worker tabs live in one window of their own, in one grey tab group titled `Kiwi Search` (not collapsed: it is the only group in that window, and collapsing a group that holds the active tab is an edge case; `tabs.group` must be given `createProperties.windowId`, because a new group otherwise goes into the *current* window, which drags the worker tab into the user's window and closes the emptied worker window), and that window is minimized right after it is created, so search pages never appear in the window the user is working in (`windows.create({ state: 'minimized' })` alone is ignored by macOS Chromium, hence the explicit `windows.update`). The window is recreated if the user closes it. Worker state is stored in `chrome.storage.session` under `kiwiRenderer`.
- `entrypoints/engines.content.ts` is injected into engine result pages (its `matches` come from `BROWSER_ENGINES`). A page handshakes with `kiwi:worker?` and gets the requested `count` and `mode`, so only registered worker tabs do anything. It watches DOM mutations (debounced), waits for `readySelector`, and extracts: it returns at once with `count` results, otherwise after the page has been quiet for 600ms, and at the 12s timeout with whatever is there. On a captcha or block page it sends `kiwi:blocked` with a `reason`: `login` when the engine's `isLoginUrl`/`loginSelector` match (a site the browser isn't signed in to: Zhihu, Xiaohongshu, X), otherwise `captcha` (`isBlockedUrl`/`blockedSelector`; use `':not(*)'` when no captcha markup is known). The pipeline then marks that source `blocked` (`source_blocked` carries the reason, `sourceStats[].blockedReason` keeps it) and extends its timeout to 120s. The new-tab page offers one action per reason ("去登录" / "去验证"), and only a captcha may bring the window forward by itself. The new-tab page shows one quiet line with a "verify" link; the worker window is brought forward only when the user clicks it (`kiwi:focus-worker`), or by itself if `renderer.focusOnCaptcha` is on. That is off by default (config migration 1→2 turned off the old saved default), and the window is minimized again once the extraction arrives.
- The new-tab page: `lib/useSearchSession.ts` owns the port, keepalive and the built-in-model summary; `lib/searchState.ts` is the pure reducer over `PipelineEvent`s; `lib/results.ts` and `lib/justify.ts` are pure helpers (`modeHasOverview` there mirrors core's `modeHasText`; importing core into the page bundle would pull in the parsers). Components are in `entrypoints/newtab/`. In a general search the community posts that the intent routes pulled in leave the list and gather in a "各平台怎么说" block after the first three results (`splitPlatforms`, at least two posts, at most six and three per platform; `PlatformStrip.tsx`) with a link into each platform's own tab; the platform tabs (知乎, 小红书, 公众号, X) are folded under one "社区" tab (`ModeTabs.tsx`, `COMMUNITY_MODES`). The page shows which engines returned a result only as small marks after the site name, and only when two or more distinct engines did (`lib/sourceMarks.ts` orders and dedupes them by rank, `entrypoints/newtab/SourceMarks.tsx` renders them: at most three, fading to the right, the rest unfold on hover or focus; none in the folded hidden section). The icons are bundled in `lib/sourceIcons.ts`, generated by `apps/extension/scripts/gen-source-icons.mjs` from Simple Icons (usage in its header), so nothing is fetched; a source without a Simple Icons glyph gets a letter badge. Beyond that, a captcha prompt is the only place a source is named. Site icons in the result headers come from the background (`lib/faviconService.ts`, message `kiwi:favicon`; `lib/favicon.ts` is the pure part): Chrome's `_favicon` API is *not* enough on its own, because it only serves icons the browser already holds from visits and bookmarks and answers every other site with the same placeholder globe (checked: GitHub, Stack Overflow, Wikipedia and a made-up host returned byte-identical 646-byte images). So the order is the browser's own icon (the placeholder is recognized by comparing with the answer for a made-up host), then the site's `/favicon.ico` and the `<link rel="icon">` of its home page (no cookies, no referrer, public host names only, image type decided from the bytes because many sites answer a missing icon with a 200 HTML page), then a letter badge. Results are cached per host in `storage.local` (`favicon:<host>`, 7 days for hits, 6 hours for misses, pruned to 400 entries), and at most 4 site requests run at once. The cost of this is that a site you have never visited receives one icon request (and one home-page request when it has no `/favicon.ico`) when it shows up in results; no third-party icon service sees your results. The URL is `newtab.html?q=…&m=images|video|academic|zhihu|xiaohongshu|wechat|x`, and new searches use `pushState`.
- Settings are in `chrome.storage.local` under `config` and `bridge` (`lib/settings.ts`); `onboarding` remembers that the first-run guide was finished, and `sourceStatus` (`lib/sourceStatus.ts`, pure part in `lib/sourceHealth.ts`) keeps what the last search that touched each source found (ok / empty / login / captcha / error), written from the pipeline events by the background and the MCP bridge. The options page (`entrypoints/options/`) autosaves (`useAutosave.ts`), groups sources by content type (`lib/sourceCatalog.ts`, typed over `SourceId`) and shows each source's status from `sourceStatus` (`lib/sourceView.ts`); the "测试连接" button sends `kiwi:test-llm` to the background (`lib/llmTest.ts`). `loadConfig` runs `migrateConfig`, then deep-merges over `DEFAULT_CONFIG`, so new config fields need defaults in `config.ts`.

**`packages/mcp`: stdio MCP server that forwards to the browser.** `src/index.ts` reads or creates the pairing token at `~/.kiwi-search/token` (`KIWI_HOME` overrides the directory). Tools are defined in `src/server.ts` (`search` and `answer` take `mode`).
- `BridgeSession` (`src/session.ts`) owns the link. The first MCP process to start binds `127.0.0.1:17345` (`KIWI_PORT`) and becomes the `BridgeHub`. It accepts the extension at `/extension`, which must present the token and a `chrome-extension://` origin, and relay clients at `/mcp`.
- Any later MCP process gets `EADDRINUSE` and becomes a `RelayClient` that talks to the existing hub. One browser connection therefore serves several MCP clients. The hub remaps request IDs (`routeId`) in `src/bridge.ts`. If the hub process exits, the relays race to bind the port again, so one of them becomes the new hub.
- The extension side is `apps/extension/lib/bridge.ts`. It runs each MCP request through the same `runSearch`, so MCP calls share the UI's queues, rate limits, cache and worker tabs. Hidden (filtered) results are left out of the tool text and listed under `structuredContent.hidden`.
- `answer` fails when the summary provider is `chrome-builtin`, because that model only runs in the new-tab page.

**Tests.** Core parser tests use saved HTML from `packages/core/test/fixtures/`. If an engine's markup changes, update its `extract` and refresh the fixture. `arxiv.xml`, `crossref.json` and `openverse.json` are real responses; `bing-images.html` is hand-written (Bing refuses non-browser clients), so it only proves the parser matches the markup we assumed. `youtube.html` (the inline data of a real response, trimmed) and `bilibili.html` (rendered DOM, first 12 cards) are real captures. No block page was captured for Bilibili, so its captcha selector is unverified. `zhihu.html` and `rednote.html` are real captures from a signed-in browser (first 10 / 12 cards, `xsec_token` replaced by `REDACTED`); `rednote.html` includes a "大家都在搜" suggestion strip that reuses the `section.note-item` markup and must not become a result. Their login-wall selectors (`.SignFlow`, `.login-container`) were only checked against signed-in pages. `duckduckgo.html` is a real capture whose snippets sit in `div[data-result="snippet"]`; the engine used to look only for older markers and read no snippet at all, and the test now asserts one per result. `weixin.html` (all 10 cards, `token=` redacted) and `sogou.html` (first 14 blocks) are real captures; Sogou's anti-spider page (`/antispider`, `#seccodeForm`) was never captured, so those are guesses. `x.html` is a real capture of a signed-in X search (6 tweets, svg/class/style stripped). It has no X Article, so that test is built by hand from the markup seen on the live page; X's signed-out page was never captured (the onboarding redirect URL was seen, the `loginButton`/`signupButton` selectors are a guess checked only against signed-in pages). Nothing automated covers the tab-rendering flow (`tabRenderer.ts`, the content script); check that by loading the unpacked extension in Chrome. The new-tab UI can be checked without the extension: serve `.output/chrome-mv3`, inject a mock `window.chrome.runtime` whose `connect()` port replays `PipelineEvent`s, and screenshot it with headless Chromium over CDP. For an end-to-end run, load the build into a headed Chromium with `--load-extension` from a **fresh copy path per build**: an unpacked extension at an unchanged path keeps running its old service worker script even after a rebuild (a version bump in the copy's manifest did not help either).
