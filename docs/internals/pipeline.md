# Search pipeline

How `runSearch` runs one search: choosing sources, timeouts and the soft deadline, the event stream, `Env`, and the cache. Overview and rules: [AGENTS.md](../../AGENTS.md). Chinese overview for people: [docs/ARCHITECTURE.md](../ARCHITECTURE.md).

## The flow

**`packages/core`: the search pipeline.** `runSearch` in `src/pipeline.ts` is the whole flow, for one `SearchMode` (`web`, `images`, `video`, `news`, `shopping`, `academic`, `zhihu`, `xiaohongshu`, `wechat`, `x`):

- pick usable sources for the mode (`usableSources` in `config.ts`) and query them in parallel, each with its own timeout. A browser source's timeout starts when it calls `onStart` (after queueing and rate limiting), not when it is enqueued. The per-source result count comes from `resultCount` (`perSourceCount`, `imageCount`, `videoCount`, `noteCount`).
- every finished source emits a partial `fused` event; with `softDeadlineMs` set (the new-tab page uses 6s, MCP does not) slow sources are left running and merged later like captcha-blocked ones (`late_results`, emitted after `done`, judged first when the judge is on). The summary is decided once, when the deadline passes: later results never start one. So if a summary is wanted and none of the sources in by then has any text, the deadline keeps waiting for the first source that does (found when a cold start left only DuckDuckGo in at 6 s, and the overview was lost for that search).

## Events and Env

Progress is emitted as `PipelineEvent`s through `onEvent`; the new-tab UI and the MCP bridge both consume that stream. Core never calls `browser.*` directly. The caller passes an `Env` with `fetch`, `cache` and, for browser engines, `runBrowserEngine`. The renderer settings travel inside `BrowserRunOptions`, so one search uses one config snapshot.

## Cache

`Env.cache` (`cache.ts`, 5 min default TTL, shared by the new-tab page and the MCP bridge) caches hits per mode/source/count/query (and, for an academic source, the language limit). News entries use a 60-second TTL and include the normalized time range and sort order, since a source may send both upstream. `RunOptions.refresh` bypasses cache reads, still writing the new result and respecting browser queues. Cached hits keep their original absolute parsed times and `news.retrievedAt`; a cache hit never makes an old relative label fresh again.

## News snapshots and filtering

News normalizes `RunOptions.news` to `range: any` and `sort: relevance` by default. One `requestedAt` anchors the rolling day/week/30-day-month cutoff for the whole run, including late results. `applyNewsOptions` runs after deterministic domain rules, after judging/reranking, and after every late merge. Date order uses known publication times before unknown ones, with relevance and normalized URL as stable ties. Strict ranges keep out old articles (`hidden: time/outside`) and uncertain publication times (`time/unknown`); a calendar day or rounded age overlapping the cutoff remains uncertain. An explicitly updated/unknown time is not treated as a publication time. Late reporting may be newer than `requestedAt` if it was already published at the source's own capture time. Explicit blocks and user-rule exclusions stay hidden. The judge cannot restore time-filtered articles to satisfy its minimum-visible fallback.

`PipelineResult.news` returns the normalized options and `requestedAt`. When an overview starts, it also records `summaryAt`, before page-text fetching; both API and built-in summaries emit `summary_start` at that point. Citation selection remains fixed for that overview. Late results are still emitted and sorted, but never automatically regenerate its text or renumber its citations. The new-tab consumer can offer an explicit overview refresh; MCP returns its completed snapshot and reports unavailable sources.

Checked 2026-11-13 with mocked sources and a fixed clock: independent cache entries for range/order/mode, explicit refresh, 60-second news expiry versus five-minute web expiry, time filtering through model scoring, date sorting after reranking, partial/late result filtering, and frozen summary citations. These unit tests make no browser or model-service calls; live activation and source markup checks are recorded separately in [news.md](news.md).

## Shopping offers

`shopping` selects only the three shopping browser sources and uses `perSourceCount`. It skips intent routing, academic planning, judging, reranking, page-content fetching and summaries through the existing non-text-mode guards. Domain rules and block lists still apply. Shopping uses URL-only fusion and bypasses Wikipedia folding; matching titles and descriptions across shops never imply the same offer. Partial and late results preserve the optional `product` fields as a single source snapshot, without mixing prices or currencies. The normal five-minute source cache applies. Amazon declares `minTimeoutMs: 60000`; the browser-source wrapper forwards that floor and the pipeline uses `max(config.sourceTimeoutMs, source.minTimeoutMs)`, starting after queueing/rate limiting. Other sources keep the configured timeout. A longer user timeout is retained, while explicit cancellation still aborts immediately. This floor allows cold minimized Amazon pages to finish streaming; it does not delay products already extracted or change the UI soft deadline.

Checked on 2026-11-13 by `shopping-pipeline.test.ts`: source/default isolation, existing choices, separate matching-title offers, product metadata in partial/late merges, and no model calls with all model features configured. Live browser coverage is recorded in [sources.md](sources.md).

## Search recovery and independently cancellable overview

The extension page's port lifecycle lives in `packages/app/src/lib/searchSessionController.ts`; `useSearchSession.ts` subscribes React to it. Each search and each explicit summary has an independent port identity. Replacing, stopping or restoring a session invalidates old listeners before closing ports, so late events cannot update the new query. Unexpected disconnects and failed keepalive writes end waiting and preserve partial results with a recoverable interruption. A normal settled port closing is not a failure. `stop()` preserves results and text while clearing running/blocked waits; `restore()` never makes a request and turns unfinished history snapshots into stopped states.

The page reducer retains source counts/errors and full completion statistics. Before a search, the background sends mode-specific enabled/ready counts from `usableSources`, allowing the UI to distinguish missing configuration from a genuinely empty search. This does not change source defaults or the source selection algorithm.

`RunOptions.summarySignal` cancels only the overview, while the existing `signal` still cancels the entire search. The summary stage is shared with `summarizeSnapshot` in `summarySnapshot.ts`; the normal automatic summary timing, source selection and MCP behavior are retained. An overview-only cancellation emits `summary_stopped` and then lets the search finish normally. MCP callers do not supply the extra signal. `onSummarySnapshot` exposes the selected evidence and preparation time to the extension without adding a second source search. Details of retry evidence are in [summary-and-language.md](summary-and-language.md).

Checked on 2026-11-13: mocked port/controller tests cover disconnects before results, after partial results and during summaries, failed keepalives, obsolete query messages, stop/restore without requests, settled disconnects, source diagnostics, summary-only cancellation and built-in streaming cancellation/timeouts. Core summary and news pipeline regression tests pass; core and MCP typecheck pass. These checks use synthetic events and mocked models, not real browser fault injection or provider requests. Final build, live activation and UI integration verification belong to the parent frontend task.

## Early overview (2026-11-15)

Where the caller sets `softDeadlineMs` (the search page, and the website only when its page says it understands the result, see "Pages that do not know the early overview" below; not MCP), `runSearch` writes a preliminary overview while the remaining sources run, so text appears before the soft deadline, judging and page reads. Settings in `summary.early` (defaults only, no migration): `minSources` 3, `waitMs` 3000, `decideMs` 5000, `keepThreshold` 0.7, `enabled`.

- **Start.** When the third source with text arrives, or after `waitMs` once at least one has text (`firstText`), whichever comes first. It uses the visible, tidied fusion at that moment (domain rules, block lists and Wikipedia folding apply; no judging) and `summarizeSnapshot(..., { excerptsOnly: true, phase: 'preliminary' })`: search excerpts only, no page reads and therefore no injection check. If the cutoff comes first, nothing changes: one final overview, with events carrying no phase.
- **Decision.** Once the preliminary overview has finished (API) or been handed to the page (`chrome-builtin`), and no earlier than `decideMs` after the search started, `judgeSufficiency` (`earlyOverview.ts`) asks the decision model one `noul` question. At or above `keepThreshold` it stands. Without a usable decision model, on a timeout (`judge.timeoutMs`) or an error, it does not.
- **Final stage.** At the usual point, after judging, the pipeline waits for the preliminary overview and the decision. A kept overview is still replaced when judging hid a result it cites (`citesHidden`). Each case emits `summary_checked { keep, reason, score?, error? }` (`reason`: `sufficient`, `insufficient`, `no-model`, `error`, `hidden`, `unfinished`). When it is not kept, the normal overview runs with `phase: 'final'`, including page reads. When it is kept, `PipelineResult.summary` and `citations` are the preliminary ones and no second model request is made. If the user stopped the overview (`summarySignal`), no final one is written.
- **Settled by judging.** When judging hid a result the preliminary overview cites, the outcome is known without the decision model (`reason: 'hidden'`, no `score`): the check that is waiting for `decideMs`, or in flight, is cancelled and the final overview is written at once.
- **Page reads beside the early overview (2026-11-16).** With an early overview in flight, the pages of the results the final overview will cite are read, and checked for prompt injection, as soon as judging has finished (`checkedContents` in `summarySnapshot.ts`, started in `runSearch` before it waits for the early overview and the decision), and handed to the final overview as `prepared`. If the early overview stands, those reads are aborted. This only overlaps with the early overview when judging ends before it does; with `selectEvidence` the reads and the final overview use the same results, so no page is read twice. Without an early overview (MCP, switched off) nothing changes.
- **One at a time.** The final overview never starts while the preliminary one is still streaming on the API path. With the built-in model, the page ends the preliminary run when the final prompt arrives.
- **News.** `summaryAt` is recorded by whichever overview chooses its citations, so it is the preliminary time when that one is kept and the final time otherwise.

Checked on 2026-11-15: `early-overview.test.ts` (12 tests, mocked sources, chat stream and decision endpoint) covers start on three sources and after the wait, no early overview without a soft deadline, when switched off or after the cutoff, keep with one model request, replacement on insufficient / failed decision / hidden citation / no decision model, `decideMs`, stopping, both built-in prompts and the evidence-only built-in check, and news `summaryAt`. The existing pipeline, summary and news tests pass unchanged (599 core tests). Live runs in the user's Chromium are recorded in [testing.md](testing.md#early-overview-activation-and-live-timing-2026-11-15).

### Early overview: requests to the overview model (2026-11-16)

`summarizeSnapshot` streams the overview through `chatStreamHedged` (`llm.ts`) with `summary.hedgeMs` (3000; 0 turns it off): when the model has sent no event at all that long after the request, an identical second request is sent, whichever sends an event first is used and the other is aborted; their texts are never mixed. An event of any kind counts, so a model that is thinking is not hedged; a request that fails before the hedge starts fails the call as before; once both are in flight one failing leaves the other; a model on this machine (`isLocalUrl`) is never hedged, since its slow start is it reading the prompt. This applies to every overview, including MCP `answer` and explicit regeneration: only latency changes, and an extra request is sent only when the first is slow.

The early overview alone is also asked not to think (`summary.early.thinking`, `off` by default): `chatStream` sends `reasoning_effort: 'none'` with `thinking: {type: 'disabled'}`, and a 400 or 422 steps down `THINKING_OFF` (each field alone, then neither) and remembers the step that worked per endpoint and model until the worker restarts. The final overview is always asked the plain way.

Checked on 2026-11-16: `llm-hedge.test.ts` (11 tests: one request when the first answers in time or hedging is off, the hedge winning, the first winning after the hedge started, no hedge for a model that is thinking, failure before the hedge, one or both failing after it, no hedge for a local model, abort of every request, the step-down ladder and its memory) and four more in `early-overview.test.ts` (thinking switch on the early request only, pages read beside the early overview and once, reads aborted when the early overview stands, no decision request when a cited result is hidden). Each of the three behaviours in the pipeline was removed in turn and the matching tests failed. 614 core tests pass. Live results and what they do not show: [testing.md](testing.md#early-overview-hedging-thinking-off-and-page-reads-2026-11-16).

### Pages that do not know the early overview (2026-11-16)

The early overview adds events a page has to know: a `phase` on every overview event, and `summary_checked`. The website (`kiwi.moe`) is deployed separately from the extension, so a newer extension can meet an older page. That happened on 2026-11-16: with the early overview activated in the owner's Chromium, `https://kiwi.moe/#q=voyage` ran for about 18 s and then the page fell back to the empty start page (and, after going back to it, "搜索尚未完成"). The deployed page's reducer had no `default` case, so `summary_checked` made it return `undefined` and the search state was cleared. Reproduced in the owner's Chromium (page text over time, no console error), and checked in the deployed bundle: it has `summary_stopped` and no `summary_checked`.

Two changes, either of which would have prevented it:

- **A page says what it understands.** The search request has an optional `phases: true` (`SearchRequest` in `packages/protocol`; the parser copies it as a boolean and ignores nothing else, so an older extension ignores it too). `packages/app`'s controller sends it. In the background, `configForPage` (`apps/extension/lib/searchConfig.ts`) turns `summary.early.enabled` off for a request without it, for that search only; the saved settings are untouched. Such a page gets the single overview it always had and no event it does not know. This protects the deployed page until it is redeployed, and any later addition of this kind.
- **A page ignores what it does not know.** `reduce` in `packages/app/src/lib/searchState.ts` now returns the state unchanged for an unknown event (it returned `undefined`). [web-app.md](web-app.md#bridge-protocol-website-to-extension) already says unknown events are ignored; the page did not do it.

Checked on 2026-11-16: tests for the parser (`phases` copied, non-boolean refused, absent unchanged), the reducer (an unknown event returns the same state; a later event still applies), the controller (the search message carries `phases: true`; an unknown event does not end the search) and `configForPage`. The reducer and controller tests failed before the change (the failure was the cause itself: the controller's state became `undefined`). The loaded build was activated at the same profile, path and ID (backup `~/.kiwi-search/backups/{bk}/`, all 486 local keys, `config` and `bridge` unchanged, executing `background.js` equal to the build); the real `https://kiwi.moe/#q=voyage` then ran to its end (44 results, 29.4 s, the quick answer shown, no console error) with two requests to the overview model and none of them an early one, and the extension's own page ran the early overview as before. Not checked: the website after a redeploy with the new page code (it will send `phases`), Firefox, a page that sends `phases` to an extension without this change (the parser change is what makes that harmless; not run). Until the website is redeployed, it has the old single overview and none of the early overview's speed.

## Model gateway headers (2026-11-16)

A user who pointed the AI model at OpenCode Go (DeepSeek Flash through `opencode.ai`) got `LLM HTTP 400: {"type":"MissingSessionID", "message":"Request is missing x-opencode-session and cannot be routed efficiently…"}` from the overview, the judge and the settings page's test button. Since 2026-09-06 that gateway refuses a request without an `x-opencode-session` header; its documentation (`opencode.ai/docs/go`, "Where can I use it?") asks a client to send one stable session id for each conversation and its own `User-Agent`. The id is a routing and prompt-cache hint, not a credential, and its value is opaque (OpenCode's own tools send `ses_` and 32 hex digits). The Zen lane ignores the header.

`withGatewayHeaders` (`packages/core/src/gateway.ts`) wraps a `fetch` and adds the header to requests whose host is `opencode.ai` or a subdomain; every other request, and a header the caller already set, passes through unchanged. The extension wraps the `fetch` of each `Env` (`makeEnv` in `background.ts`) and the one in the settings test (`lib/llmTest.ts`). One `makeEnv()` is one search, one overview or one MCP request, so the decision model, the judge and the overview of one search share a session id and the next search gets a new one. The id is made when the first request to the gateway needs it. Core itself still sets no vendor header; a host that builds its own `Env` has to wrap its `fetch` the same way.

Not done: a product-specific `User-Agent`. A service worker's `fetch` ignores it (a request that set `User-Agent: kiwi-test/1` reached the server with the browser's own), and the documentation says "should", not "must". Gateways other than OpenCode that need a header are not handled.

Checked on 2026-11-16: `gateway.test.ts` (7: the plain request fails with the reported body, a completion and a stream succeed through the wrapper, one id per search and a new one for the next, no id for other hosts or look-alike names, a caller's header and the rest of the request kept, the host test, the id shape) and `llmTest.test.ts` (2, one of which failed when the wrapper was taken out of `llmTest.ts`). In a throwaway Chromium (fresh profile) in which `opencode.ai` resolved to a local HTTPS stand-in that answers 400 `MissingSessionID` to a request without the header: the build loaded in the owner's browser at that time reproduced the report (the test button and an overview over the `summary` port both ended in that 400), and the build with the change succeeded on both, the gateway receiving a `ses_…` id on each request and a different one for the two operations. Not checked: the real OpenCode gateway (there was no account or key, so what is known is from its documentation and from several users' reports that the header alone is enough); that a Go plan's terms allow this use (its page says Go is for coding agents and that traffic is monitored); Firefox.
