# Tests, fixtures and manual verification

Which fixtures are real captures and which are hand-written, and what only a real browser can check. Overview and rules: [AGENTS.md](../../AGENTS.md). Chinese overview for people: [docs/DEVELOPMENT.md](../DEVELOPMENT.md).

## Fixtures and parser tests

**Tests.** Core parser tests use saved HTML from `packages/core/test/fixtures/`. If an engine's markup changes, update its `extract` and refresh the fixture. `arxiv.xml`, `crossref.json` and `openverse.json` are real responses; `bing-images.html` is hand-written (Bing refuses non-browser clients), so it only proves the parser matches the markup we assumed. `youtube.html` (the inline data of a real response, trimmed) and `bilibili.html` (rendered DOM, first 12 cards) are real captures. No block page was captured for Bilibili, so its captcha selector is unverified. `zhihu.html` and `rednote.html` are real captures from a signed-in browser (first 10 / 12 cards, `xsec_token` replaced by `REDACTED`); `rednote.html` includes a "大家都在搜" suggestion strip that reuses the `section.note-item` markup and must not become a result. Their login-wall selectors (`.SignFlow`, `.login-container`) were only checked against signed-in pages. `duckduckgo.html` is a real capture whose snippets sit in `div[data-result="snippet"]`; the engine used to look only for older markers and read no snippet at all, and the test now asserts one per result. `weixin.html` (all 10 cards, `token=` redacted) and `sogou.html` (first 14 blocks) are real captures; Sogou's anti-spider page (`/antispider`, `#seccodeForm`) was never captured, so those are guesses. `x.html` is a real capture of a signed-in X search (6 tweets, svg/class/style stripped). It has no X Article, so that test is built by hand from the markup seen on the live page; X's signed-out page was never captured (the onboarding redirect URL was seen, the `loginButton`/`signupButton` selectors are a guess checked only against signed-in pages). The academic sources' tests are in `academic.test.ts`. Real: `pubmed-esearch.json`, `pubmed-efetch.xml` (reference lists trimmed), `europepmc.json`, `europepmc-preprints.json`, `baiduxueshu.html` (all 10 cards, scripts/SVG/popover videos removed), and the block pages `baiduxueshu-blocked.html`, `cnki-blocked.html`, `wos-blocked.html` (scripts removed, captcha key/token and client IP redacted) plus `dblp-challenge.html` (DBLP's bot check). Hand-written, each saying so in its first line or a `_note` key: `dblp.json` (the API was behind the bot check), `cnki.html` and `wos.html` (a captcha and a login in front of the real result pages), so their tests only prove the parsers match the markup they were written against. The `blockedUrl` map in `parsers.test.ts` needs no entry for these engines because each has a real `<id>-blocked.html`. The block-list parser's fixture `blocklist-excerpts.txt` is verbatim lines picked from the four real lists checked in [blocklists.md](blocklists.md) (sections name each); the tests in `blocklist.test.ts` pin the shapes found there (regexes with unescaped inner slashes and trailing comments, wildcard hosts, `$doc,reason="…"`, section rules, exceptions, IPv4, cosmetic filters, a fullwidth-colon typo).

## Douyin and Yuanbao fixtures (2026-11-13)

`yuanbao.html` is a real rendered, signed-out `so.qq.com` result page: 16 cards, of which 14 are results and two are related-search strips. Scripts/styles/SVG were removed and session/signature parameters redacted. `yuanbao.test.ts` checks the ordinary web-search route, title and snippet extraction (including an encyclopedia card), and rejects duplicate, internal and non-HTTP links. No Yuanbao block page was observed, so the generic block-page test intentionally excludes it.

`douyin-blocked.html` is a real signed-out video-search page, captured on 2026-11-13. It is a login wall, not a captcha; scripts/styles/SVG, QR-code images and inputs were removed. Both the available headed Chromium profile and the separate browser session were signed out, so this fixture does not establish that signed-in video extraction works.

`douyin.html` is hand-written from the site's current public frontend modules, with synthetic video IDs/titles and an explicit provenance header. `douyin.test.ts` checks the video-tab URL, video-only extraction, metadata, deduplication, unsafe/foreign URL rejection, exclusion of prediction cards and other lists, and the real login wall. It does not replace a signed-in capture; successful-result rendering still needs live verification. `douyin-captcha.html` is the real same-URL captcha interstitial encountered in fresh extension worker tabs. Its scripts/styles and iframe query (fingerprint, challenge data and environment) were removed. The parser test recognizes the captcha iframe and rejects a page that merely preloads the captcha SDK.

## What is not automated, and how to check it

Nothing automated covers the tab-rendering flow (`tabRenderer.ts`, the content script); check that by loading the unpacked extension in Chrome. The new-tab UI can be checked without the extension: serve `.output/chrome-mv3`, inject a mock `window.chrome.runtime` whose `connect()` port replays `PipelineEvent`s, and screenshot it with headless Chromium over CDP. For an isolated end-to-end run, use a separate Chromium profile and a fresh build-copy path. This avoids a previously observed stale service worker, but is a QA technique, not the way to update the user's live browser: without a manifest `key`, changing the resolved extension path changes its ID and storage namespace.

## Activate completed changes in the user's local Chromium

The user requires every completed extension change to take effect in the existing local Chromium while preserving settings, API keys, pairing data, browser logins and other data. A successful build or an isolated QA run does not complete this step.

1. Identify the existing browser profile, loaded extension path and extension ID. Keep all three; update that ID instead of loading a second copy. If multiple Kiwi copies exist, inspect their paths and storage before changing anything; back up both and disable an obsolete copy rather than uninstalling it.
2. Snapshot extension storage before updating (`local`, `sync` and `session` where available), and retain the previous build. Backups can contain credentials: keep them outside the repository under `~/.kiwi-search/backups/`, restrict directories to `0700` and files to `0600`, and never print their contents. Do not replace the user's config with a QA config or clear storage. See [config-and-storage.md](config-and-storage.md).
3. Build, copy the build into the existing loaded directory, and use the matching extension's **Reload** button in `chrome://extensions`. Do not move to a fresh path, add a new manifest key, remove/reinstall the extension, or replace the profile. Keep unrelated tabs and site storage intact.
4. Verify the actual running service-worker source against the build, not only a fetch of the file on disk. Over CDP, `Debugger.getScriptSource` gives the executing source for a hash comparison. Also check `chrome.runtime.id`, the running `chrome.runtime.getManifest()` (including content-script matches), and the changed behavior in a newly opened or reloaded extension page.
5. Compare saved storage values with the snapshot, particularly `config`, `bridge` and keys. Canonical JSON comparison avoids object-key ordering differences. Explain any intentional migration; unexpected differences must be investigated before declaring success. Session storage is temporary and may be reset by a reload, so preserve what is needed before reloading and do not treat it as persistent configuration.

## Continuous integration (2026-11-13)

`.github/workflows/ci.yml` runs on pushes to `master`, on pull requests and on manual dispatch (`gh workflow run ci.yml`), with Node 24 and pnpm 12 as the README asks. One job, `verify`, runs: `pnpm install --frozen-lockfile`, `pnpm typecheck`, the core, extension and mcp suites as separate steps, the extension and mcp builds, then uploads the unpacked `.output/chrome-mv3` as the `kiwi-search-chrome-mv3` artifact (14 days). The root `pnpm test` is not used because `packages/experiments` has no tests and exits 1. Typecheck and the three test steps use `if: ${{ !cancelled() }}`, so one failing step does not hide the others; the builds and the upload run only when everything before them passed.

Checked on 2026-11-13:

- A fresh `git clone` of the repo, `pnpm install --frozen-lockfile` with pnpm 12.18.0 (local Node was 26.13.1), then typecheck, 545 core + 235 extension + 17 mcp tests, and both builds: all passed. The clone had none of the git-ignored local files, so nothing the build needs is missing from the repository.
- On GitHub: the pull-request run (PR #2), the push to `master` and a manual dispatch all passed with every step executed, none skipped. The extension artifact was uploaded (449,300 bytes).
- Failure path: a throwaway PR (#3, closed, branch deleted) added a type error in `packages/mcp/src` and a failing core test. The run went red on exactly those two (`TS2322`, `expected 1 to be 2`), the extension and mcp suites still ran and passed, and the builds and the upload were skipped.

Known limit seen in that failing run: `pnpm -r typecheck` stops at the first failing package and sends SIGTERM to the rest, so a type error is reported for one package only. `pnpm -r --no-bail typecheck` would report all of them; the workflow does not use it and that variant was not run.

Not checked: any runner other than `ubuntu-latest`, any Node version other than 24 on GitHub, whether the pnpm store cache (`cache: true` in `pnpm/action-setup`) is restored on a later run, the Firefox build (not in CI; see "Firefox" below for the live check), and installing the uploaded artifact in a browser. CI does not replace the real-browser checks above.

## Firefox

`build:firefox` writes `apps/extension/.output/firefox-mv2`; load its `manifest.json` from `about:debugging` → "Load Temporary Add-on". Browser-specific code reads `import.meta.env.FIREFOX`: `wxt.config.ts` leaves out the `favicon` permission, `faviconService.ts` skips `_favicon`, and the onboarding (`StartSection.tsx`) shows a copyable `about:preferences#search` because Firefox won't let an extension open its settings pages. The MCP hub accepts `moz-extension://` origins. In Firefox the `KIWI_EXTENSION_ID` value is the per-install UUID shown in `about:debugging`.

Checked on 2026-11-13 with Firefox 160 on macOS, using a fresh profile and no model keys:
- The temporary add-on loads without the `favicon` warning. The remaining build warnings are a missing extension ID and `data_collection_permissions`.
- New tab, web search (merged Google/Bing/DuckDuckGo/Brave), images, video, news, shopping (Amazon), academic and WeChat all returned results.
- The full-tab settings persist across a reload. A Content Farm Terminator subscription downloaded 20,547 rules, and the 360-minute alarm exists.
- `https://s.kiwi.moe/s?q=test` is intercepted.
- Following the onboarding in Firefox works. The real labels are "Default Search Engine → Add" and a dialog with name, URL and optional keyword. Afterwards, an address-bar search opens Kiwi.
- With an empty token there are no `_favicon` requests and no localhost WebSocket errors.
- A real MCP stdio `search` returned results through Firefox with `KIWI_EXTENSION_ID` set to its UUID, and a wrong UUID got HTTP 403.
- In a throwaway Chrome profile, the MV3 build still shows the Chrome settings button and keeps `favicon`.

Not checked: AI overview and quick answer, successful results from login- or captcha-gated platforms (Zhihu, RedNote, X, Taobao, JD, Google Scholar), whether the Openverse 504, Bilibili refusal and X timeout also happen in Chrome, the user's own Chromium profile, and AMO signing.
