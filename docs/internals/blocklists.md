# Block lists

Parsing, compiling and applying block lists in core, and how the extension stores, downloads and refreshes subscriptions. Overview and rules: [AGENTS.md](../../AGENTS.md). Chinese overview for people: [docs/BLOCKLISTS.md](../BLOCKLISTS.md).

## Core: syntax, rules and what hides a result

**Block lists** (`blocklist.ts`, no key needed): `config.judge.blocklists` holds `recommended` (ids from `RECOMMENDED_BLOCKLISTS`; all off by default, because a subscription is a request to a third-party host), `subscriptions` (the user's own `{id, name, url, enabled}`; https only, plain http only for localhost: `isSubscriptionUrl`) and `custom` (the user's own rules as text). `parseBlocklist` reads one syntax per line: plain domains (`example.com`, `*.example.com`, leading-dot `.example.com`, `example.com/path`, wildcard hosts `foo.blogspot.*`, IPv4), hosts-file lines, uBlock Origin / Adblock Plus network filters (`||x^`, `||x/path^`, `|https://x/y`; options `$doc`/`$all`/`$document`/`$important` and the `reason="…"` annotation the AI uBlock Blacklist puts on every line are accepted, any other option such as `$script` or `$third-party` makes the rule unsupported), uBlacklist match patterns (`*://*.x/*` is the site and its subdomains, `*://x/*` is that one host, `*://x/blog/*` a section), `/regex/` lines, and exceptions (`@@…` and `@…`). Page-element filters (`##`, `#@#`…), comments, a leading `---` header block and anything else that cannot be matched against a search result are skipped and counted (`stats.cosmetic`, `stats.unsupported` with a few `examples`). `www.` is not told apart from the bare domain. A regex is kept only if it names a site (`example\.com`), has no `(a+)+`-style nested quantifier or backreference, is at most 400 chars and does not match two of three unrelated probe URLs; this is a heuristic, not a proof, and it also drops URL-shape regexes like `/.*\/(.*)(s|q)=.*/` that would hide ordinary pages. The check applies only to regexes someone wrote (a list's `/…/` line, a `|` filter), not to the ones built from a validated host. The parsed `BlockRules` (`block` and `allow`, each `sites` / `hosts` / `patterns`) are plain JSON; `compileBlocklist` indexes them (a `Set` walked up the host's labels for sites and hosts, a linear scan of regexes against the first 2048 chars of the URL, one memo per search, the index itself kept per rules object in a `WeakMap`). `runSearch` starts `loadBlocklist(config, env)` beside the sources (never awaited before they start, never rejects) and every list of results, partial `fused` events included, goes through `applyDomainRules(results, judge, lists)`; before this the partial events skipped domain rules, so blocked results showed until the soft deadline. What hides a result, in order: the user's own `blockedDomains` (no list name); otherwise an exception in any list, or the user boosting the site, keeps it; otherwise the first list that matches (`HiddenReason` is `{ reason: 'blocked', list?: name }`, which the page and the MCP `hidden` entries show). `Env.loadBlocklists(settings)` supplies the subscribed lists' parsed rules; the user's `custom` text is parsed in core (`parseBlocklistCached`). Checked on 2026-11-12 against the real lists (Content Farm Terminator 20.5k rules incl. 3.3k regexes and wildcard hosts, 4 lines unusable; AI uBlock Blacklist 2.6k; BadWebsiteBlocklist 418 incl. 204 section rules; eallion's uBlacklist 15.6k, 1.7k of its lines being cosmetic filters): `packages/core/test/fixtures/blocklist-excerpts.txt` is verbatim lines of them; 100 non-matching results against all four lists took about 39 ms, once per URL. eallion's compilation is deliberately **not** in the catalog: it also carries its author's taste (all of baidu.com, csdn.net, juejin.cn, amazon.com and sohu.com are in it); the three that are in hide none of 62 popular sites' home pages.

## Extension: subscriptions, storage and refresh

Block-list subscriptions live in the extension: `lib/blocklistService.ts` (storage and fetching) over `lib/blocklistState.ts` (pure: what is due, how a download is read, the status wording). `storage.local` holds `blocklistMeta` (small, per list: address, `fetchedAt`, `attemptedAt`, `etag`, rule counts, `error`, `updatingSince`; the settings page watches it) and `blocklist:<id>` (the parsed rules, large: about 630 KB for the 20.5k-rule list). The background refreshes a list when the worker starts (a no-op unless one is due), on an alarm every 6 hours (created only if absent: creating a named alarm again restarts it, and the worker restarts more often than that), when `activeSubscriptions` changes in a stored config (switching one on, adding one, changing an address; editing the custom text does not) and on `kiwi:blocklist-refresh` (the settings page's "立即更新", forced). A list is due after 24 h, or 1 h after a failure; a download sends no cookies and no referrer, uses the kept `ETag` for a 304, is capped at 12 MB and 30 s, and a list that parses to zero rules is an error. A failed refresh keeps the rules from before (the status line says so). Switching a recommended list off or removing a subscription deletes its stored rules (`prune`); the parsed rules of a list are kept in memory per worker so a search does not parse megabytes of JSON. `makeEnv` in `background.ts` passes `loadBlocklists`, so the MCP bridge hides the same results. The panel is `entrypoints/options/BlocklistsPanel.tsx` (inside the "屏蔽与偏好" section, reusing the source-row styles): recommended lists with a switch and a status line, subscriptions by address, the custom text with a live count of what was understood, and a syntax cheat sheet. Reset to defaults clears all of it. Checked on 2026-11-12 in headless Chromium 156 with a throwaway profile (`--load-extension`, lists served from localhost): setting the config in storage made the worker download and store the real 20.5k-rule list by itself, `kiwi:blocklist-refresh` answered, the panel rendered the status, and a real web search folded blog.csdn.net and github.com results as "命中屏蔽列表「…」" while the other six stayed. Later the same day, with the user's own Exa key as the only enabled source (a real Exa search, 10 results, in a throwaway headless Chromium; harness kept outside the repo in `~/.kiwi-search/e2e/`), 24 checks passed: a subscription served from localhost is downloaded by the worker by itself and folds the right Exa results with the list's name; an `@@` exception and the user's own rules (label 自定义规则) work; a forced refresh sends the kept ETag and a 304 keeps the rules and the download time; an HTTP 500 and a 200 page with no rules are reported as errors while the old rules keep hiding results; a changed list replaces the rules; switching a list off hides nothing and removing it (even one already switched off) forgets its stored rules; the three recommended lists download from their real addresses through the extension (20,547 / 2,636 / 418 rules) and hide nothing in an ordinary search. Not seen live: the 6-hour alarm firing, Firefox.
