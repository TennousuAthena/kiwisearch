# Extension runtime: background, worker tabs, content script

The service worker, how browser engines run in worker tabs, and the content script that reads their result pages. Overview and rules: [AGENTS.md](../../AGENTS.md). Chinese overview for people: [docs/ARCHITECTURE.md](../ARCHITECTURE.md).

## Overview

**`apps/extension`: WXT + React, Manifest V3.** `entrypoints/` holds the entry points.

## Background service worker

`background.ts` is the service worker and runs the pipeline. The search page (`app.html`, the extension's own interface) opens a `runtime.connect({ name: 'search' })` port, sends a `search` request (`query`, `mode`), and receives streamed `PortMessage`s. The same file registers the omnibox keyword, declarativeNetRequest redirects for the addresses of `kiwi.moe` and of the old host `s.kiwi.moe` that depend on the interface source (`lib/searchRedirect.ts`, re-registered whenever the setting `uiSource` changes), the toolbar button (opens `app.html`), the `kiwi:*` runtime messages, and the MCP bridge with its reconnect alarm. `makeEnv` also gives core `Env.redirectTarget` (`lib/redirectTarget.ts`, built on `webRequest.onBeforeRedirect`, so the manifest asks for `webRequest`): it tells where one of Google's `/goto` result links leads without waiting for the page behind it (see [sources.md](sources.md)). The service worker also answers the Kiwi website: `entrypoints/web-bridge.content.ts` relays a page's private `MessagePort` to it as `kiwi-web:*` messages and the `search`, `summary` and `web-push` ports, and `lib/webBridge.ts` checks the sender and every request before anything runs (design, limits and checks in [web-app.md](web-app.md)). The options page only opens on first install. It is declared `open_in_tab` (the meta tag `manifest.open_in_tab` in `entrypoints/options/index.html`; WXT's default is `false`), so "Extension options" opens a full tab instead of the small embedded view inside chrome://extensions.

## Worker tabs (`lib/tabRenderer.ts`)

Browser engines run in `lib/tabRenderer.ts`. Each `SourceId` has its own serial queue and a minimum interval between requests (`renderer.minIntervalMs`). Each engine gets one persistent, muted worker tab. All worker tabs live in one window of their own, in one grey tab group titled `Kiwi Search` (not collapsed: it is the only group in that window, and collapsing a group that holds the active tab is an edge case; `tabs.group` must be given `createProperties.windowId`, because a new group otherwise goes into the *current* window, which drags the worker tab into the user's window and closes the emptied worker window), and that window is minimized right after it is created, so search pages never appear in the window the user is working in (`windows.create({ state: 'minimized' })` alone is ignored by macOS Chromium, hence the explicit `windows.update`). The window is recreated if the user closes it. Worker state is stored in `chrome.storage.session` under `kiwiRenderer`.

## Content script (`entrypoints/engines.content.ts`)

`entrypoints/engines.content.ts` and `entrypoints/shopping.content.ts` are injected into engine result pages (its `matches` come from `BROWSER_ENGINES`). A page handshakes with `kiwi:worker?` and gets the requested `count` and `mode`, so only registered worker tabs do anything. It watches DOM mutations (debounced), waits for `readySelector`, and extracts: it returns at once with `count` results, otherwise after the page has been quiet for 600ms, and at the 12s timeout with whatever is there. On a captcha or block page it sends `kiwi:blocked` with a `reason`: `login` when the engine's `isLoginUrl`/`loginSelector` match (a site the browser isn't signed in to: Zhihu, Xiaohongshu, X), otherwise `captcha` (`isBlockedUrl`/`blockedSelector`; use `':not(*)'` when no captcha markup is known). The pipeline then marks that source `blocked` (`source_blocked` carries the reason, `sourceStats[].blockedReason` keeps it) and extends its timeout to 120s. The new-tab page offers one action per reason ("去登录" / "去验证"), and only a captcha may bring the window forward by itself. Two more ways a worker page fails fast instead of waiting out the timeout: an engine's `refusedPattern` matching the page text (the site refuses outright; the content script sends `kiwi:refused`, e.g. Zhihu's risk-control JSON `code 40362`), and a page that finished loading but whose content script never said hello within 4s (`HANDSHAKE_GRACE_MS` in `tabRenderer.ts`: the browser's own error page, an HTTP 403 that keeps the requested address, a redirect to a page the engine doesn't read). Both reject the request, which `sourceStatus` records as "上次出错" with the reason. Checked in a fresh, signed-out headless Chromium: Zhihu answered the search URL with that JSON (0.8s to fail, was 13.8s) and X with Chrome's 403 page (5.0s, was 15s); a real signed-out Zhihu/X login wall was NOT seen there, so `loginSelector`/`isLoginUrl` for those are still guesses. The new-tab page shows one quiet line with a "verify" link; the worker window is brought forward only when the user clicks it (`kiwi:focus-worker`), or by itself if `renderer.focusOnCaptcha` is on. That is off by default (config migration 1→2 turned off the old saved default), and the window is minimized again once the extraction arrives.

## News request plumbing

The search port and MCP bridge pass `news: {range, sort}` and `refresh` into `RunOptions`. Browser sources forward news conditions through `BrowserRunOptions` into the fifth `buildUrl` argument. The content script fixes one extraction clock per worker-page handshake and supplies it to every `extract` observation, so relative ages do not drift while DOM mutations settle. No new storage setting, migration, worker window or source identity is introduced.


## Shopping document startup

The shared runner is `lib/engineContent.ts`. Ordinary sources keep the `engines.content.ts` entry at `document_idle`; shopping sources have a disjoint `shopping.content.ts` entry at `document_start`. A cold Amazon response in a minimized worker stayed in `loading` while products were visible; waiting for document idle missed the handshake and source deadlines. The early runner first confirms the active worker identity with the background, then observes the document itself (which works before `documentElement` exists), including streamed text and relevant image/link attributes. Even when enough products exist, it waits for the normal quiet interval so fields can settle. It does not read an ordinary user tab that fails the handshake.

Amazon declares `minTimeoutMs: 60000`. The pipeline uses the greater of that floor and the user's general source timeout, starting after queueing; cancellation remains immediate. Its early content runner gets 57 seconds, leaving the background time to receive a result. Taobao/JD retain the ordinary timeout. No timeout or renderer setting is rewritten in storage.

Checked on 2026-11-13: runner tests cover an unregistered user tab, a document without its root element, streamed price fields, normal idle-source completion, login blocking and delayed product arrival. Core tests cover the timeout floor, longer user settings, queue timing and cancellation. After activation at the original extension ID/path, a real shopping query showed Taobao/Tmall and Amazon products while JD reported login. This is runtime verification of the early entry; tests alone do not prove Chrome content-script injection. See [shopping.md](shopping.md).
