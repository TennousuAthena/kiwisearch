# Config and storage

The config version and migrations, defaults for new fields, and what the extension keeps in `chrome.storage.local`. Overview and rules: [AGENTS.md](../../AGENTS.md). Chinese overview for people: [docs/ARCHITECTURE.md](../ARCHITECTURE.md).

## Config version and migrations

Config has a `version` (`CONFIG_VERSION`); put rewrites of stored configs in `MIGRATIONS` in `config.ts`. `baidu` is off by default and last in `BROWSER_ENGINES` (the options page groups sources by content type in `lib/sourceCatalog.ts`, in the order of that file): its result page mixes in widgets (translate cards, recommendation lists, hosts like `nourl.ubs.baidu.com`) that the parser reads as results. Migration 2→3 switched it off in stored configs, and switching it on in the options page opens a confirmation dialog (`confirm` in its `SOURCE_INFO` entry). New fields only need defaults.

Douyin (`douyin`, video) and Yuanbao (`yuanbao`, web) are opt-in: both have explicit `{ enabled: false }` defaults. No version bump or migration is needed; merging older configs adds the disabled entries while preserving an explicit user choice to enable either source. The settings page groups them under video and web respectively. Kagi (`kagi`, web) is opt-in the same way (`{ enabled: false }`, no migration); it also sets `confirm: 'source.confirm.kagi'` in `SOURCE_INFO`, so the options page asks before it is switched on (see [sources.md](sources.md)).

Checked on 2026-11-13: configuration tests cover fresh defaults, merging older saved settings and retaining explicit opt-ins. An isolated Chromium profile loaded from a fresh build-copy path showed both switches off; enabling them through the settings page and reloading preserved the choices. No changes were made to the user's existing browser settings.

Later on 2026-11-13, the build was activated in the user's existing Chromium at the same extension path and ID. The live settings page showed both new sources off, while all 588 saved local-storage entries, including `config` and `bridge`, retained their values; `storage.sync` was unchanged. The new defaults are merged when settings load, so adding the switches did not require rewriting the saved config. The activation and backup record is in [testing.md](testing.md).

## Settings storage and the options page

Settings are in `chrome.storage.local` under `config` and `bridge` (`lib/settings.ts`); `onboarding` remembers that the first-run guide was finished, `academicLanguage` the language the academic tab was last limited to (`packages/app/src/lib/academicLanguage.ts`; a page preference kept out of the search configuration), and `sourceStatus` (`lib/sourceStatus.ts`, pure part in `lib/sourceHealth.ts`) keeps what the last search that touched each source found (ok / empty / login / captcha / error), written from the pipeline events by the background and the MCP bridge. The options page (`entrypoints/options/`) autosaves (`useAutosave.ts`), groups sources by content type (`lib/sourceCatalog.ts`, typed over `SourceId`) and shows each source's status from `sourceStatus` (`lib/sourceView.ts`); the "测试连接" button sends `kiwi:test-llm` to the background (`lib/llmTest.ts`). `loadConfig` runs `migrateConfig`, then deep-merges over `DEFAULT_CONFIG`, so new config fields need defaults in `config.ts`.

### Drafts and concurrent writers

The options page renders a loading or retry screen until its real config and bridge values have loaded. Default objects are never exposed as editable controls after a failed read. Source-health and blocklist metadata are supplementary and do not block the settings form. `autosaveQueue.ts` debounces ordinary saves, coalesces intervening edits to the newest draft, and retains failed drafts for the explicit retry button. The hook records each committed render in a layout effect. On `visibilitychange`/`pagehide`, `handoff()` sends the newest draft immediately even while an older request is awaiting its response; repeated hide events do not resend an identical pending draft. Once received, these requests are serialized by the background independently of whether the page survives to receive their replies. Storage failure or browser/process termination still cannot be represented as a successful save; the page reports success only after its latest submission has succeeded.

`saveConfig(next, baseline)`, `saveBridge(next, baseline)` and `saveSettings(next, baseline)` compare against the last successfully saved draft. `lib/configUpdates.ts` sends only changed leaf values over `kiwi:update-settings`; `lib/backgroundConfig.ts` is the single serialized writer, loading the latest stored value before applying each change. The background accepts these mutations only from this extension's new-tab or options page. Config and bridge patches from one options save are written together. Different fields edited in different pages are preserved; concurrent changes to the same scalar field follow background processing order. The page does not silently replace an in-progress draft with another page's edits.

A handoff supplies all unacknowledged/uncertain local snapshots to `saveSettings(next, baseline, superseded)`. `diffSettingsFromBaselines` merges their differences against the latest draft: this includes a change reverted to the last saved value while an older write is pending, and retains an older local edit when that earlier request fails. Domain additions/removals are merged by membership, so an unrelated page's added domain survives either outcome. Only fields touched by the local snapshots are sent. Failed responses remain uncertain until a successful later save repairs them; the options baseline advances monotonically by submission version so a delayed old reply cannot replace the newer baseline.

`judge.blockedDomains` and `judge.boostedDomains` use membership additions/removals rather than replacing their entire arrays. Result-page block/boost/clear actions use the same queue, normalize the domain, and keep that domain's block and boost states mutually exclusive. The returned undo receipt restores only the affected domain. `domainPreferenceRevisions` stores opaque per-domain receipt revisions separately from `config`; later edits of that domain invalidate older receipts, including a sequence that returns to the same state. Undo never overwrites another domain's edits, and invalidated receipts report that restoration did not occur. The client helper has no runtime import of core, so result-page actions do not pull search parsers into the page bundle.

### Finding settings and page preferences

Sources can be searched by their name, ID or description and filtered to all/enabled/needs-attention. Attention uses the warning/error states from `describeSource`: enabled sources missing a required key/address, or with recorded login/captcha/error failures. A normal untried login source, an empty result, or a disabled source is not classified as a failure. A source being edited remains visible and expanded until focus leaves its fields, so typing the first credential character cannot remove the row mid-edit. Group counts describe the visible rows. Group presets are hidden during filtering so a visible subset cannot conceal a wider batch change; disabling a row in an enabled/attention filter moves focus to a remaining row or the search field. Preset undo is kept per group and includes only switches changed by that preset; manual later changes remove that switch from the receipt. It updates only `enabled`, preserving keys, weights, other settings and other groups. Filtering temporarily hides the preset controls but retains their undo receipts.

Segmented choices have one Tab stop and support arrow/Home/End navigation. Visible switch titles are associated labels. The section navigation reports the current section with `aria-current` and opens the advanced section when reached by its anchor.

Appearance and search-display preferences live in independent `ui:theme`, `ui:summaryMode`, `ui:openNewTab` and `ui:recentQueries` keys, managed by `packages/app/src/lib/uiPreferences.ts` and shared between quick settings and `UiPreferencesPanel`. They are outside core config and outside the options autosave draft. The recent-query preference is a boolean; query text itself is not written by these settings helpers.

`ui:summaryMode` is the extension UI's only overview-generation setting: `auto`, `on-demand` or `off`. When that key has no valid value, initialization reads the old `config.summary.enabled` value: explicit `false` maps to `off`; every other case maps to `auto`. This is a read-only compatibility fallback, with no migration write or change to config, API keys or MCP settings. Explicit UI choices, including `auto`, take precedence over the old bit. The new-tab page sends an explicit `summarize` boolean on each search. The options AI section always exposes model/language fields and links to the same three-way preference instead of keeping a second switch. The legacy core field remains available to MCP callers using the existing automatic-summary behavior.

Storage changes synchronize open pages. Config changes affect the fallback only while no valid UI mode is saved; removing the UI key restores that fallback. Initial reads merge changes that arrived while loading, and a delayed local write response cannot overwrite a later storage event. Only the old summary-enabled bit is retained from config by the preferences store. Checked on 2026-11-13 with mocked storage: legacy mapping, explicit-mode precedence, no writes on initialization, two-page change propagation, key removal, changes during initial read, delayed write responses and retry after storage failures. These tests do not inject failures into the live browser.

Checked on 2026-11-13: extension typecheck and the full extension suite passed (235 tests in 28 files). Configuration/autosave checks cover unrelated multi-page edits, serialized overlapping writes, domain membership merging, conditional undo, optional-object sibling preservation, failure recovery, no initial write, coalescing, attention classification and preset undo scope. Handoff tests verify immediate submission before an older response, duplicate hide events, reverting an in-flight edit, an older failure repaired by a newer request, and a latest failure remaining retryable without a false success state. Integration tests hold the older storage write pending and never deliver page responses, then verify that the handed-off latest draft persists after either success or failure of the older write while preserving another page's domain edit. Not checked in this implementation pass: real-browser storage failure injection, controls with assistive technology, and settings changes in the existing live extension; live activation/verification is recorded separately in the project testing and status records.

## Preserve data during local activation

The user's existing profile and extension identity are part of the development workflow. Before activating a completed change, snapshot available extension storage and retain the previous build, then update the existing loaded path and ID instead of loading a second copy. Do not uninstall the extension, clear storage, substitute test settings, or create a fresh live profile. Browser logins live in the browser profile and site storage; extension updates must not replace or clear them. A fresh extension path without a manifest `key` generates a different ID, so a fresh-copy QA run is not an update of the existing extension. If duplicate copies already exist, inspect and back up each one's storage before disabling the obsolete copy; do not discard either copy's data.

Storage exports include API keys and pairing credentials. Store them outside the repository in `~/.kiwi-search/backups/`, with directories `0700` and files `0600`; report only locations, counts and comparison results, never values. Compare the persisted data after activation, and account explicitly for any intended config migration. `storage.session` is temporary and is not a substitute for a persistent backup. Follow the activation checks in [testing.md](testing.md), including both the running code and manifest: reloading code alone does not prove that new content-script matches are active.

## Shopping sources

Taobao (`taobao`), JD (`jd`) and Amazon US (`amazon`) have explicit enabled defaults. They are available only in `shopping`, so enabling them does not add requests to web searches. Existing configs gain these defaults when merged in memory; saved settings, keys and explicit per-source choices are preserved. No config version bump or migration is required.

Checked on 2026-11-13 for shopping activation: the original profile/extension ID/path were retained and saved config, keys, bridge and sync storage matched the protected pre-update snapshot. Only source-status records and favicon cache entries changed during live checks; cache pruning is the existing favicon service behavior. See [shopping.md](shopping.md).
