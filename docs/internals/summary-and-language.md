# AI overview and its language

The summary prompt and its citations, and how the overview language is chosen. Overview and rules: [AGENTS.md](../../AGENTS.md). Chinese overview for people: [docs/ARCHITECTURE.md](../ARCHITECTURE.md).

## Summary

optional summary with `[n]` citations (`summarize.ts`, page text from `content.ts`; its language is `summary.language`, below), only from non-hidden results; community posts (Zhihu, WeChat, Xiaohongshu) are labelled `Platform:` in the prompt and, when the sources mix platforms and ordinary pages, the model is asked to say what each platform says and how they differ (only differences the sources show); images, video and Xiaohongshu notes get no summary and no judging, Zhihu answers do (`modeHasText` in `types.ts` decides). `content.ts` never fetches zhihu/xiaohongshu/rednote pages (a plain fetch hits the login wall); their own excerpt is used. Academic mode uses a literature-overview prompt.

## Quick answers in general search

In `web` mode, the same summary request also decides whether the query is one objective factual question that the supplied evidence can answer briefly. It does not use a question mark as the classifier. Eligible answers reserve the first Markdown H1 for a short, plain-text conclusion (at most 12 words, about 30 Chinese characters, always under 100 characters), followed by one explanatory paragraph of 1–3 sentences under 600 characters with inline source citations. The model stops there, so the result page can promote that answer above the first search result without repeating an overview beside it. The full Markdown remains readable by MCP and other consumers; API and Chrome built-in summaries receive the same instructions. No extra classification or answer request is added, and summary settings, language selection and the frozen citation snapshot remain shared.

The prompt prefers official or primary evidence and requires the year/date, statistical metric and geographic scope for changing figures such as population. A dated result is allowed without pretending it is current or the latest. Navigation, broad research, open-ended questions, opinions, recommendations, personalized medical/legal/financial advice, insufficient evidence and unresolved conflicts use the ordinary overview, whose headings start at `##`. User style instructions remain available but do not override evidence, citations, language or this format. Eligibility and factual grounding are model judgments; the UI's format and citation checks cannot independently establish that a claim is true. UI extraction and layout are documented in [newtab-page.md](newtab-page.md).

Checked on 2026-11-13: `summary.test.ts` checks the web-only format contract, temporal/statistical requirements, ordinary-overview fallback instructions, language and custom-style precedence, one API summary request with intact Markdown/citations, and delivery of the same format to the built-in model without an API request. All 531 core tests passed. These tests use synthetic evidence and mocked model output; they do not measure real-model compliance or verify the running browser UI.

Live checks on 2026-11-13 used the original Chromium profile, original extension ID and existing model/search settings: `香港有多少个区` and `深圳市的人口是多少` both produced a cited quick answer above the first result without a duplicate overview or empty rail. The population answer explicitly identified the end of 2025 and resident population, linking the Shenzhen statistics bureau and other supplied results. The two completed searches took approximately 22.5 and 20.5 seconds respectively under the existing search/judge/page-reading settings; quick answer adds no separate model call, but does not remove that existing pipeline latency. The Hong Kong run reported a pre-existing judge timeout and still completed its summary. Screenshots and DOM observations are in `/tmp/kiwi-quick-answer-live/`. A third real query, `深圳旅游攻略`, retained a normal overview and showed no quick-answer block. These three queries exercise one configured API model; they are not a factual-accuracy evaluation. Live Chrome built-in output, Firefox and other providers were not tested.

## News evidence snapshot

In news mode the prompt names each publisher, keeps the full available publication/update timestamp and original time label, records source retrieval time, and distinguishes page text from a search excerpt. The prompt requires attribution for developing or disputed claims, reporting both sides of a conflict with citations, and never confusing publication, update, event and retrieval times. It does not claim the results are comprehensive or verified through the snapshot time. `summaryAt` is captured when citation selection starts, before optional page reads; cached source text retains its earlier retrieval time. Sources arriving later do not change that summary or its citation numbering. The UI can offer a new overview on explicit refresh.

Checked 2026-11-13: prompt tests cover publisher/full-time context, conflict guidance, unknown time and excerpt scope; pipeline tests cover the same citation snapshot across partial and late result events and `summary_start` before the built-in prompt. No external LLM was called for these tests, so model compliance with the news wording is not yet measured.

## Explicit overview generation and retry

`summarySnapshot.ts` reuses the existing citation builder, prompt (including quick-answer rules), language selection, page fetching and prompt-injection checks. It never calls search sources, intent routing or ranking. A first generation selects non-hidden text results in citation order, emits the existing summary events and exposes a snapshot before/after optional page reads. Only checked page content is retained in that snapshot; rejected content cannot reappear on retry. Stopping or failing while page checks are in progress leaves an excerpt-only snapshot, including the interval between the initial summary event and the prepared snapshot message.

The extension's separate `summary` port accepts explicit generation even when automatic overview generation is off; it reads the user's current model configuration without changing the saved setting. The background only accepts these ports from this extension's new-tab/options pages. The request parser bounds query length, result count, overall payload and individual text sizes, requires text modes and HTTP(S) source URLs, and rejects malformed basic result metadata. Browser content scripts and foreign extension/page senders cannot invoke this route.

The hook's `summarize()` retries `summaryResults`, including already checked page text and the original `summaryAt`, without re-fetching pages. `summarize({ fresh: true })` selects the current visible evidence and prepares a new snapshot. Both keep the search result list in place. News retries retain the previous evidence fingerprint and stale indicator; a fresh overview updates its evidence and timestamp. A manually generated overview may start before the search finishes: later fusion/judging as well as late-source merges mark changed news evidence stale, and search completion preserves the overview timestamp. Citation numbers are rebuilt only from the fixed selected order. The automatic search path and the independent path both use the same API or Chrome built-in prompt. Built-in generation remains in the page, with a 60-second inactivity timeout and an AbortController; stopping ignores any late chunks and preserves already generated text.

Checked on 2026-11-13: `summary-snapshot.test.ts` verifies one streamed API summary without source searches, unchanged citation order and checked text on retry, fresh page reads only on explicit refresh, rejected-content removal, built-in prompt parity, and independent versus whole-search cancellation. Extension controller and request-boundary tests cover snapshot retry/fresh behavior, original timestamps, stopped partial text, obsolete streams, built-in cancellation/timeouts, and sender/payload validation. Existing quick-answer prompt and news tests pass unchanged. No real model, browser fault injection or complete UI interaction was exercised by these unit tests; those require the frontend task's live verification record.

## Overview language

**Overview language** (`language.ts`): `summary.language` is `browser` (default), `auto`, `custom` (text in `summary.languageCustom`) or a BCP 47 tag from `OVERVIEW_LANGUAGES` (20 languages, each labelled in itself). Core has no browser to ask, so the browser's first language comes in as `Env.browserLanguage`: `makeEnv` in `background.ts` sets it at every search from `navigator.languages[0]` (the Accept-Language order; `chrome.i18n.getUILanguage()` only when that is empty), via `lib/language.ts` `browserLanguage()`, so the page, the options page and MCP all agree. `overviewLanguage(summary, browserLanguage)` gives the name to write in or `undefined`: `undefined` is `auto`, and also the fallback when the browser says nothing usable or the setting is not understood, and leaves the old rule \"Answer in the same language as the query\". A name comes from `Intl.DisplayNames` (English, so `pt-BR` is \"Brazilian Portuguese\"); Chinese is told by script (Traditional for TW, HK, MO and `Hant`, else Simplified); a custom text is cut to one line of letters, digits and little punctuation, at most 40 characters, and a code typed there (`fr`) is read as a code. With a language, `buildSummaryMessages` writes \"The answer MUST be written in X. This holds even when the query and the sources are in another language: do not answer in the language of the query. …\" in the system prompt AND ends the user turn with `(Write your answer in X.)`. Measured with the dev model (deepseek-flash) on real Chinese sources asked to answer in English or Japanese, 4 trials each: the first wording (one \"Write the whole answer in X\" rule in the system prompt) was followed 8 times in 12; with only the reminder added 10 in 12; with the stronger rule plus the reminder 12 in 12. Small samples, one model; other models may differ. The same messages go to the API model, to Chrome's built-in model (`summary_prompt`, run by the page) and to MCP `answer`. Chrome's Prompt API takes only en, ja, es, de and fr as output (its documentation, read 2026-11-12; others \"in development\"), so the settings page warns when the built-in model is chosen with another language (`builtinModelWrites` in `lib/language.ts`; custom names that are not codes get no warning, `auto` none); `builtinModel.ts` still creates its session without naming a language. Default `browser` means a browser whose preferred language is English answers in English even for a Chinese query: the dev browser reports `en-GB, en-US, en`; choose `auto` to follow the query. Checked 2026-11-12 in throwaway headless Chromium with Exa and the dev LLM: an English browser (default 4 of 4 English on a Chinese query, auto, ja, zh-CN, zh-TW, a custom \"Italiano\" all right) and a browser whose `intl.accept_languages` is `zh-CN` (default gives Chinese for both an English and a Chinese query; auto gives English for an English query); the settings page was driven by real events (stored values, hints, the notice) and screenshot in light and dark. `--lang=zh-CN` did not change `navigator.languages` on this Mac, `intl.accept_languages` in the profile's Preferences did. Not checked: Firefox, a Chinese-UI Chrome in daily use, other models' compliance, MCP `answer` end to end (it shares the pipeline, covered by the unit tests).
