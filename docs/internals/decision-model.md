# Decision model, intent routing and the judge

The provider layer that answers the search's small questions, how the query's intent starts extra sources and suggests a tab, and how results are judged. Overview and rules: [AGENTS.md](../../AGENTS.md). Chinese overview for people: [docs/DECISION-PROVIDERS.md](../DECISION-PROVIDERS.md).

## The decision model

**The decision model** (`decision.ts`, protocol in `docs/DECISION-PROVIDERS.md`) answers the small questions the search asks (is this a paper search? is that page filler?). It is a provider layer, not TypeSafe: `judge.provider` is `systemone` (default; a dedicated model behind `judge.endpoint`, which speaks System One's request/response: TypeSafe's Jev is only the preset, any service implementing the protocol can be pointed at, keyless if it runs on this machine), `llm` (only the user's chat model) or `none`. The dedicated model is the recommended one (about 0.9 s for the intent verdict against 2.9 s for a chat model, and one cheap request per result); the user's OpenAI-compatible chat model (`decisionLlm(config)`: the AI-overview model `config.llm` while `judge.llmShared`, else `judge.llm`) is the fallback, used when no dedicated model is set up, or when it refuses outright (`isHardFailure`: a 4xx other than 408/429, e.g. a 401 bad key or a 451 region block, or no connection; never a timeout, 429 or 5xx) and `judge.fallbackToLlm` is on. `resolveDecisionProvider(config)` says who would answer now; `decisionModelUsable` (= `judgeEnabled`) whether anyone can. Everything asks through `askDecision` and gets System One's shape back (`answers: {id: {noul|score}}`), so thresholds, hiding and routing are the same for every provider. The chat-model path sends the questions as one JSON chat request (`chatForJson`: JSON mode, and again without it when the provider answers 400/422; replies are clamped, a 0-100 probability is scaled, a skipped question is left out) and judges results ten per request, three requests at a time, instead of one per result; if the dedicated model refused every per-result request, the batch path takes over. Chat models are slower (the dev reasoning model: intent 1.7-5.8 s, twelve results 4.5 s), so the defaults are `intent.timeoutMs` 8 s and `judge.timeoutMs` 12 s (config migrations 3→4→5 widen the old 3 s / 6 s and rename `typesafe` to `systemone`), and the search waits past the soft deadline for a verdict still on its way (what it switches on is then late and merges in afterwards). The settings page tests a dedicated model with `kiwi:test-decision` (`handleDecisionTest` in `lib/llmTest.ts`). Checked live 2026-11-12: the dev chat model's verdicts match Jev's on 17 queries (杭州三日游攻略 xhs 0.97, 猫咪图片 images 0.99, 周杰伦 演唱会 video 0.95, weather/documentation ~0); the four cases dedicated / nothing configured / refused (wrong key) / refused with fallback off behave as above; the example server in the protocol document works unchanged.

## Intent routing in the general mode

In the general (`web`) mode, when the decision model is on, `intent.ts` asks it about the query alone (academic? Zhihu? Xiaohongshu? WeChat? images? video? six Noul questions) while the general sources are already running. Routes at or above `intent.threshold` start their sources mid-search (`launch` in `pipeline.ts`), each in its own mode so it builds its own URL and shares its own cache, and join the same fusion; a `routed` event reports the verdict. No key, an error, `intent.timeoutMs` (3s) or a verdict that arrives after the soft deadline just leaves the general sources. Not used with explicit `sources` or in other modes. The `routed` event also carries `suggest` (`IntentSuggestion`: the best of academic / images / video at or above `intent.threshold`, `strong` when at or above `intent.switchThreshold` and `intent.autoSwitch`). The new-tab page decides what to do with it in `lib/suggestion.ts`: when `strong`, the search was typed (or the page opened with it) and no results are showing yet, it moves to that tab by itself (`history.replaceState`) and says so with a way back ("返回网页结果"); otherwise, or after a Back or a reload, it only offers the tab in one line. Without a usable decision model none of this runs and nothing says so (it is a choice the settings page explains); when one is set and the verdict fails, the `routed` event's `error` becomes `SearchState.intentError` and the status line says so, in one line when the filter failed for the same reason (`decisionModelNotes` and `explainServiceError` in `lib/results.ts`, which put HTTP 451 / 401 / 429 into words). Checked live on 2026-11-12 with the real model (`api.typesafe.ai` reachable from Node): platform-style queries score 0.8-0.98 (杭州三日游攻略: zhihu 0.96, xiaohongshu 0.96, wechat 0.82), weather, documentation and a random token score under 0.4, so 0.6 behaves sensibly; the 0.85 auto-switch only fired for 猫咪图片 (images 0.99) and 周杰伦 演唱会 (video 0.87). From the browser the same endpoint answered 3 requests and then HTTP 451 \"not available in your region\" for the next 7, while curl got 10 of 10: the browser's connections left through another proxy exit, so a proxy needs a direct or supported-region rule for `api.typesafe.ai` (one more reason the decision model is not tied to TypeSafe). The 0.6 and 0.85 thresholds are still a first guess, from about 17 queries.

## The judge

`judge.ts` (through the decision model; TypeSafe: one request per result): relevance Score, junk Noul, one Noul per user rule. It orders results and flags some as `hidden`; when active it replaces `rerank.ts`. It also checks fetched page text for prompt injection before summarizing.
