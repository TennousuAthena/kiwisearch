# Sources

The source registry, browser engines and API sources, Exa snippets, the two Brave sources, and what adding a source touches. Overview and rules: [AGENTS.md](../../AGENTS.md). Chinese overview for people: [docs/DEVELOPMENT.md](../DEVELOPMENT.md).

## Registry, browser engines and API sources

Sources are unified as `SearchSource` and registered in `src/sources/index.ts` (`SOURCES`). Each declares `modes`, `requiresKey` and, if needed, `requiresBaseUrl`/`requiresBrowser`:

- Browser engines (`google`, `bing`, `baidu`, `duckduckgo`, `bravesearch`, `kagi`, `scholar`, `baiduxueshu`, `cnki`, `wos`, `yandex`, `youtube`, `bilibili`, `douyin`, `zhihu`, `xiaohongshu`, `rednote`, `sogou`, `yuanbao`, `weixin`, `x`, `taobao`, `jd`, `amazon`) are `BrowserEngine` objects in `src/engines/*.ts`: `buildUrl(query, count, mode, language?)` (`language` is set only for an academic search limited to a language; Google Scholar is the one engine that uses it, see [academic.md](academic.md)), `matches`, `readySelector` (a selector list covering all modes), `blockedSelector`, `isBlockedUrl`, `extract(doc, pageUrl, mode)`, and an optional `resolve` for unwrapping redirect links. `makeBrowserSource` in `engines/shared.ts` wraps them as sources. Bing serves web and images through the same worker tab and queue. The YouTube engine reads the inline `ytInitialData` JSON from the page's scripts (so its `readySelector` is just `body`) instead of the custom-element DOM; the Bilibili engine reads the rendered `.bili-video-card` DOM. Zhihu and Xiaohongshu only work in a browser the user is signed in to. Xiaohongshu has two sources, `xiaohongshu` (mainland) and `rednote` (international), with separate domains and logins but the same note ids (normalized to `xhs:<id>` in `url.ts`, so both merge); `rednote` is on by default and the mainland site is opt-in. Note links keep `xsec_token`/`xsec_source`, which the site needs to open a note. Zhihu keeps its author in `meta.author`, not `meta.authors`, because `authors` marks a result as a paper for de-duplication and would merge different answers to one question. The Sogou WeChat engine (`weixin`, mode `wechat`) finds WeChat official-account articles; it returns Sogou's own redirect links (`/link?url=…`), which, opened without a Referer, land on the article at mp.weixin.qq.com (checked), so they are kept as they are and `host` is set to `mp.weixin.qq.com`. The publish time comes from the text of the `timeConvert('<unix seconds>')` script, which is never run. `sogou` (Sogou web search, off by default) also keeps redirect links and takes the site from a card's `data-url`. Neither needs a login. X (`x`, mode `x`) works only in a browser signed in to X (signed out, a search redirects to `/i/jf/onboarding/web`, which `isBlockedUrl` recognizes). It is a tab of its own and never a route of the general search; its tweets are not judged or summarized (`modeHasText('x')` is false). X polices automated use of an account, so the engine sets `BrowserEngine.minIntervalMs` (10 s), which `tabRenderer.ts` applies on top of `renderer.minIntervalMs` between request *starts*. X renders a virtualized list and renders nothing new while the worker window is minimized (page visibility `hidden`; scrolling the worker page changed nothing), so a search returns only the 4–6 tweets of the first render, and getting more would mean bringing the window forward. The engine skips promoted tweets (a bare `Ad` label), takes a quote tweet's own text instead of the quoted one's, uses the title and preview of an X Article when a post has no tweet text, and reads the counts from the `aria-label` of the action row.
- API sources (`brave`, `exa`, `deepseek`, `openalex`, `crossref`, `arxiv`, `openverse`, `pubmed`, `europepmc`, `dblp`, `searxng`) live in `src/sources/*.ts` and call HTTP through `env.fetch`. Openverse is anonymous-limited (20 results per page, 200 requests a day).

## Exa snippets

Exa returns a page as Markdown (both `text` and `highlights`; its docs call it "plain markdown-style text"), and a page often opens with a table: Wikipedia with its infobox, an annual report with pages of them. The snippet used to be `highlights[0] ?? text` squeezed to one line and cut at 300, so a result showed `| 浙江稠州商业银行股份有限公司 … | | | --- | --- | …` (seen by the user on the Wikipedia page of 浙江稠州商业银行). No Exa setting avoids it: checked with the user's key on three queries, a highlight capped at 600 characters even starts inside the table (`| --- | --- |`), and `excludeSections` changed nothing on these pages. `contents.summary` (Exa writes a description) is clean, 0 of 10 with a table, but costs 4-5 s more (5.3-6.3 s against 1.2 s) and $0.017 against $0.007 a search, which would push Exa past the 6 s soft deadline every time, so it is not used. Instead `markdownSnippet` in `text.ts` makes the snippet: it splits the Markdown into blocks and takes the first block with something to say, in page order (so a footer never comes before the content): a paragraph of prose (and the next ones until about 240 characters; a paragraph ending in a colon also takes the list after it), a list whose items are longer than menu entries, or a table of three or more columns (a ranking is what its page is about; read as `排名 地区 GDP；1 广东 …`). A two-column table is an infobox and is skipped for the prose after it; headings, code, the repeated page title and any line with a `|` (header, footer, breadcrumb) are not prose; links, images, footnote marks like `[9]`, emphasis, tags and zero-width marks are stripped; lines wrapped inside a sentence are joined without a space between two CJK characters. It reads the highlight first and `text` when the highlight has nothing; with no content block at all it falls back to a list, then a table read as `label：value` pairs, then short lines. `content` stays Markdown (the overview and the decision model read it fine). The request now uses `highlights.maxCharacters` 1500: `numSentences` is deprecated (about 1,333 characters a sentence, so "3 sentences" was up to 4,000) and `highlightsPerUrl` is ignored (every answer carried an `IGNORED_FIELD` warning). `packages/core/test/fixtures/exa.json` is 12 real results (10 for 浙江稠州商业银行, plus a five-column ranking table and an article whose text opens with a `### 来源 | … | …` byline), trimmed. Checked 2026-11-12: over 130 real results from five request shapes none kept table syntax or Markdown marks and none was empty; in the user's dev browser through the real pipeline (Exa only) 30 results on three queries were clean, at the same 1.2-2.0 s. Not checked: DeepSeek's `snippet` and SearXNG's `content` are used as given (no key for the first; the second is plain text by its API); a `[a]` or `[1]` that is real content in a snippet is dropped with the footnote marks.

## Brave: two sources over one index

Brave has two sources over one index, like the two Xiaohongshu sites: `brave` (API, needs a key; `sources/brave.ts`) and `bravesearch` (`engines/bravesearch.ts`, web and news modes, no key, on by default), which reads `search.brave.com/search?q=…&source=web` in a worker tab for web mode (the news route is described below). Web results are `.snippet[data-type="web"]` blocks (the page also holds an AI answer, an FAQ and a `cluster`, other `data-type`s that are skipped); the title is `.search-snippet-title` inside the link, the snippet `.generic-snippet .content` (Brave already writes the date into it, `31 March 2025 - …`, which is kept as text and not parsed into `publishedAt`), or `.inline-qa-question` for a Reddit-style card; links are direct, so there is no `resolve`. Brave's slider captcha is served at the **same address** as the results (title `Captcha - Brave Search`, `.captcha-wrapper`, `canvas.captcha-image-canvas`), so `isBlockedUrl` is not defined and `blockedSelector` does the work. Both sources share one mark (`SOURCE_MARKS`), so a result both returned is not shown as two engines agreeing; with both switched on Brave is counted twice in the RRF fusion (not deduplicated; the settings blurb says one is enough). Checked on 2026-11-12: `bravesearch.html` is the rendered DOM read from the user's own dev browser (20 results, scripts/styles/SVG removed) and `bravesearch-blocked.html` is the captcha page a cold headless Chromium got (same query, `HeadlessChrome` user agent; curl with a Chrome user agent got results, the dev browser got results and no captcha). In the real extension: the dev browser, Brave (web) as the only source through the real pipeline, 10 results in 3.2 s cold and 1.0 s warm (English and Chinese queries), status `ok`; a throwaway headless Chromium with only this source got the captcha, the content script reported it (`captcha`) and the page showed "去验证". Not known: how often an ordinary new browser is sent to the captcha, so the on-by-default choice is a guess; that verification covered only web mode (news support was added on 2026-11-13 as described below; images and videos are not read).

## Google result links (`/goto`)

Google's results page wraps a result's link as `https://www.google.com/goto?url=<token>`: 21 of the 26 anchors in `google.html`, all 13 in `google-news.html`. The token is encrypted (no address in it, and the anchor's `ping` attribute holds the same kind of token), so the extractor keeps the wrapper and `google.resolve` asks Google where it leads. A wrapper that stays is a result whose link, host-level merging and content fetching are all worse: the fusion can only match it to other engines' results by host and title, and the overview skips its page.

**What was wrong (reported 2026-11-14: some Google results showed `google.com/goto?url=…` as their link).** Two separate causes, found in that order.

1. *The old resolver was slow and threw answers away.* `resolve` used `fetch`, which follows the redirect and answers only when the *destination* does, and it began with `if (!response.ok) return hit`: the destination's status was taken for Google's. Measured with the 13 real links of `google-news.html` (captured the day before, so *aged* links), a service-worker `fetch` with no cookies in a throwaway headless Chromium: following the redirect took 1.0 to 4.3 s per link, wsj.com and reuters.com answered 401, and the original `google.resolve` (from `origin/master`) left **6 of 13 results wrapped, after 5.8 s**. Reading Google's `Location` directly is not possible: `fetch(…, { redirect: 'manual' })` gives an `opaqueredirect` response in the extension too (status 0, no headers).
2. *Google does not always answer with a redirect.* Found only afterwards, with fresh links in the user's own browser (the aged links of the first measurement never showed it). In 3 of 5 real searches through the activated extension, 8 of the 10 `/goto` requests were answered with a 200 page instead of a 302 (the page: about 16 KB, title `Google`, its text mentions "verif" and "redirect"); in the other 2 all 10 were redirected. In a window like that, four links polled every 3 s for 42 s stayed at 200. It is not the age of a link: links of a fresh render were redirected at once in a good window. No resolver can do anything while Google answers 200, the old one included, so this, not 401s, probably accounts for the 8 unresolved links the user first saw (not recorded at the time; the same links resolved when fetched later). Other people report the same behavior ("Verifying your request" after resolving many links at once; Greasyfork, 2026-10-30). Its cause here is not known.

**The change.**
- `google.resolve` takes the address the redirect ended at whatever the page there answered. This alone covers the 401/403 case and needs nothing else.
- `Env.redirectTarget` (new, optional; `RedirectTarget` in `types.ts`) answers where Google sends a link without waiting for the page. The extension builds it in `lib/redirectTarget.ts` from `fetch` and `webRequest.onBeforeRedirect`: the first redirect that changes the host is the answer, and the request is aborted at once. Redirects that stay on the host are followed by request id. Core takes the answer only if it is a web address that is not on Google. Without `webRequest`, or when no redirect is reported, the address `fetch` ended at is used, and the response body is cancelled instead of downloaded. Core, the MCP bridge and the page all get it through `makeEnv`.
- **New permission: `webRequest`** (observe only; no `webRequestBlocking`). `wxt.config.ts` adds it for every browser. It is separable: removing the permission and the `redirectTarget` line in `background.ts` leaves the first change in place.

**Measured (2026-11-14).**
- Throwaway headless Chromium 156 with fresh profiles, a scratch extension with the `webRequest` permission, and the 13 aged links: `onBeforeRedirect` fires for a service-worker `fetch` (`tabId` -1, type `xmlhttprequest`) with the destination in `redirectUrl`, usually about 0.2 s after the request (up to 1.7 s). On abort the request to the destination is announced about 1 ms after the redirect and ends `net::ERR_ABORTED` within the same millisecond (6 of 6); whether anything reaches the destination before that was not checked at network level. The real `createRedirectTarget`, bundled unchanged from the repo: 13 of 13, about 0.2 s each; with the 5 workers `resolve` uses, 614 ms for all 13, the same answers as one at a time. The original and the new `google.resolve` on the same 13 links: **6 of 13 wrappers left in 5.8 s, against 0 of 13 in 0.78 s.** These were aged links, so this measures the cost of following redirects and of 401s, not Google's refusals.
- In the user's browser, with the activated build: the real `createRedirectTarget` injected into the extension's service worker, against the 17 real links of the worker page: 17 of 17 in 3.9 s one at a time and 17 of 17 in 1.1 s with 5 workers.
- Five real Google-only searches (query `typescript handbook`, no overview, settings untouched) through the activated extension and the whole pipeline: 2 resolved all 10 results (0 wrappers; the source finished in 1.0 s and 2.0 s), 3 left 8 of 10 wrapped. In the 2 of those that were recorded request by request, the 10 `/goto` requests ended as 2 redirects, 6 answers of 200 and 2 aborted in one, and 2 redirects, 4 answers of 200 and 4 aborted in the other (who aborted those requests was not found). The worker page itself held 17 `/goto` links and no direct link.
- Four links of a fresh render requested with `redirect: 'manual'` in a good window, in four ways, all redirected: the service worker without cookies (as shipped), with `credentials: 'include'`, with a Google referrer, and from the worker page itself (same origin, its cookies). The same four ways were not tried in a bad window.
- Tests: 9 for `redirectTarget` (extension) and 9 more for `google.resolve` (core: error statuses, Google-hosted or non-web answers, abort signal, de-duplication, the browser source passing it on). Undoing each of 8 parts of the change fails at least one test.

**Not checked.**
- Why Google answers 200 in some windows (a throttle on its side, or something about this machine's network exit: the Mac routes through a proxy), and whether anything gets past it. In particular, whether a request with cookies, a referrer or from the worker page passes in a bad window (the four ways above were tried in a good one only). scraping.club reports that wrapped links are served to clients Google classifies as automated, for example Chrome started with `--remote-debugging-port` (one experiment: 213 direct links without the flag, none with it); the dev browser runs with that flag and its worker page had 17 wrapped links and no direct one, but it was not compared with a browser without the flag, and ScrapingBee saw wrapped links in manually operated Chrome and Edge as well.
- Firefox: built (the manifest has the permission) but not run; there the fallback covers a missing event. Chrome's own list of permissions (read 2026-11-14) shows no install warning for `webRequest`, and an extension in the Chrome Web Store reads the same redirects the same way.
- A wrapper that stays unresolved is still a working link (Google redirects when it is opened) and keeps its host from the result's `cite` text where there is one; only merging with other engines, content fetching for the overview and what MCP clients receive are worse.

**How others handle it (read 2026-11-14).** Request `/goto` with redirects off and read the `302 Location`; `HEAD` answers 200 without a `Location`, as `redirect: 'manual'` shows no `Location` here; the token is protobuf around Tink-style ciphertext and differs on every render, so it cannot be decoded or tabulated (scrapingbee.com/blog/google-goto-redirect-urls, magstags.com/notes/google-goto-url-redirect). Google's page keeps the real address in its own script state (`W_jd`) for some result types, which userscripts read; it is not kept for news and its layout changed within a day (Rob--W/dont-track-me-google, issue 67), so it was not used. dont-track-me-google resolves only when the user interacts with a link.

## Douyin and Yuanbao (opt-in)

Both sources use the existing browser renderer without API keys and have explicit disabled defaults. Douyin (`douyin`) belongs to video mode; Yuanbao (`yuanbao`, `so.qq.com`) belongs to web mode. They add no search modes. Older saved configs inherit the disabled defaults, while explicit enabled choices survive merging.

Douyin uses `https://www.douyin.com/search/<encoded query>?type=video`. It reads only the video-tab list (`ul.PAjzsG5a > li .search-result-card`), excludes hidden prediction cards, and accepts only numeric video paths on the official Douyin host; user cards, live rooms and recommendations outside that list are not results. It extracts the title, cover, duration, author and displayed date from the current frontend's CSS classes. The cover counter is likes (`meta.votes`), not playback views, and the author profile uses a click handler rather than a link, so `video.channelUrl` is absent. Checked on 2026-11-13: two signed-out browser sessions reached the real login wall (`#douyin_login_comp_flat_panel_title`), captured in `douyin-blocked.html`. The optional header login button is not used as a login-wall signal. The successful-result fixture `douyin.html` is **hand-written**, reconstructed from Douyin's public search bundles (its header records the URLs and module IDs), not a signed-in capture. Signed-in extraction, thumbnail loading and successful-result rendering in a minimized window remain unverified. Fresh extension worker tabs instead received a captcha interstitial at the unchanged search URL: the parent page has almost no visible text but contains an iframe under `https://rmc.bytedance.com/verifycenter/captcha/`. That iframe is the captcha signal; merely loading the captcha SDK is not. `douyin-captcha.html` captures the real interstitial with its scripts and complete iframe query removed.

Yuanbao uses the ordinary search URL `https://so.qq.com/isearch?query=…&quick=1`, not the site's AI chat mode. It reads `.result-card` containers and the semantic `linkid` values in their links' `data-log` JSON: `title` or `header_title` for the main link, `summary` or `description` for the snippet. Those attributes are parsed as data, never evaluated. Related-search strips and extra links inside a card do not become results; non-HTTP links and links back into `so.qq.com` are skipped. Result links are direct, so there is no redirect resolver. Checked on 2026-11-13: signed-out headed Chromium returned real results for the minimal URL, and `yuanbao.html` captures the rendered cards (scripts/styles/SVG removed; session and signature values redacted). No login or captcha wall was observed; `blockedSelector` is deliberately `:not(*)` until a real verification page supplies a selector.

Integration checked on 2026-11-13: core 477 tests, extension 150 tests and MCP 15 tests passed; workspace typecheck and build passed. The built manifest includes both sites' content-script patterns. Fresh build-copy paths and isolated Chromium profiles verified both settings switches start off, appear in the correct groups, and persist after enabling and reloading. Through the real extension pipeline, Yuanbao returned 10 results for `猫` in about 1.5 seconds in both headless and headed Chromium. Douyin's real captcha interstitial initially produced an empty result; after adding the iframe selector, a fresh build reported `source_blocked` with reason `captcha` while the worker window stayed hidden. The login wall itself was checked on real pages and in its fixture, but a successful signed-in Douyin search and manual captcha completion were not checked. The existing user's browser profile and source settings were not changed.

## Kagi (opt-in)

`kagi` (web mode, `engines/kagi.ts`) reads `https://kagi.com/search?q=…` in a worker tab, in whatever Kagi session the browser has. There is no key; Kagi's own Search API (invite-only, billed separately, under separate API terms) is not used. Kagi is a paid search engine and a search in a signed-in browser counts against the account's usage (a plan with a limit has a monthly quota; not checked here), so the source is off by default (`{ enabled: false }`, no version bump or migration) and the options page asks first (`source.confirm.kagi`). Kagi's terms (`kagi.com/privacy#Terms-of-use`, read on 2026-11-13) say nothing either way about automated access to the search pages; they say frontend products are for non-commercial use only, that Kagi may suspend an account at any time, and that they grant no right to use its logos (the bundled icon is used as the other engines' are, see `NOTICE.md`). The API terms (`kagi.com/privacy/api`) forbid scraping and bulk copying of results but cover the API only. Whether reading the page from the user's own browser is acceptable to Kagi is not settled here; it is the user's call.

- **Extraction, checked against real pages (2026-11-13):** `kagi.html` is the rendered DOM of a real results page read from a browser with no Kagi session (10 main results, 4 grouped ones) and `kagi-signed-in.html` one read in a browser signed in to a trial account (trimmed from 28 main results and 6 grouped ones to 11 and 6; the rest, including pages of individuals' accounts, were left out). A second signed-out page (35 main results, 1 grouped one) and the full signed-in page were also run through the extractor offline and not kept. A main result is `.search-result` (class `_0_SRI search-result`); its link is `a.__sri_title_link`, with a direct absolute `href` (plus `data-domain` and `title`); its snippet is `.__sri-desc`, cut at 300. `.__sri-desc` also holds a date badge (`span.__sri-time`) and, on a signed-in page, a Summarize link (`a.summarize-link`, on every result) whose label follows the interface language (`Summarise` on the en-GB page; other tools quote `Summarize`); both are removed, because the date used to lead the snippet and the link's label would end it. The only other element seen inside a description is `strong`. A result can be followed by a sibling `.sr-group` of more pages from the same site (`.__srgi` rows, title in `.__srgi-title a`): they are results too but are appended after all the main ones, because in page order they take ranks 2 to 5 and, in the fusion, lift one site's sub-pages above every other engine's results. With the default `perSourceCount` of 10 and ten main results they are cut off. Only absolute `http(s)` hrefs count. A page Kagi could not title is listed as `Link to <domain>` with no snippet (one in each of the two pages with 35 and 28 results); it is kept as Kagi shows it. The news, video and Wikipedia modules and the related searches use other classes and are skipped (none was among the results of the captured pages; the hand-written `kagi-edge-cases.html` covers them). Dates and thumbnails are not read.
- **What a browser with no Kagi session meets (2026-11-13, Chromium 156, fresh profiles):** `/search` answers 302 to `/turnstile?r=<the search>`, a Cloudflare Turnstile page (`.cf-turnstile`, `data-appearance="interaction-only"`; `kagi-blocked.html` is the real page). The engine reports `captcha` from it, 1.8 to 7.9 s after the request in five runs. In the three headed runs where the worker window was made visible the check passed by itself (nothing was clicked) after about 26, 60 and 70 s, the tab went to `/search?q=…` and real results appeared. In the two runs where the source was still waiting (the source timeout had been raised to 170 s) the engine extracted them (10 hits, delivered as `late_results`); in the third the source had already ended with the 15 s timeout, so nothing was extracted. Being signed out is therefore not a login wall. In the other three runs it did not pass: headed and minimized for 63 s, headless for 27 s and for 128 s (the default-config run ended with `source_error: timeout after 120000ms`; a blocked source is held for up to 120 s, not the 15 s source timeout). Whether the window being visible matters was not established (the passes took 26 to 70 s, longer than two of the failed observations; the headless browser identifies itself as `HeadlessChrome` and no attempt was made to hide that). A second search in the same browser went straight through: no `/turnstile` visit, results in about 2 s. A signed-out page shows its allowance in the header (`Searches used 1/50`, next to "Log In" / "Sign Up"; the limit itself was not tested) and a "Create Account" button under the results (`._0_share_url_footer`); none of it is a wall, and before the results are rendered the button is all the page shows. The sign-in (`/signin` to `account.kagi.com/loginname`) was seen only by requesting `/signin` with curl: no search went there, so `isLoginUrl` and its two `matches` patterns are untested in the extension flow.
- **Signed in (2026-11-13, the user's own browser, read-only: the tab's DOM and its navigation history, no search sent from here):** the account is a trial one, and the header reads `Searches used 2/150` with an "Upgrade now" link instead of the "Log In" / "Sign Up" bar (`.auth-bar-links` is absent). Every Kiwi search through this source would spend one of those searches. A results address typed into the address bar (`/search?q=…`, as the extension opens it) went straight to results: the tab's history holds the typed address and `/search` and no `/turnstile`. That is one observation, in an ordinary tab and not in a worker tab, and an earlier search submitted from Kagi's home page showed no verification either. The extension has not been run in this signed-in browser (see [testing.md](testing.md)).
- **Evidence for the selectors besides the capture:** Kagi's custom-CSS guide (`help.kagi.com/kagi/features/custom-css.html`) and tools written against the live page (tcode, serp-axi, kagi-cli, Apollo-Reborn, macproxy_plus, kagi-ken). They agree with the capture, and are where the date span, the Summarize link and the sibling `.sr-group` structure were first seen. kagi_ex's fixtures are, by its own test header, "simplified copies" of the Rust SDK's, so it is not independent evidence. Two real pages for the same query in two sessions listed different results (the captured fixture and the pipeline run of the last test), so a result list is not stable between sessions.
- **Known limit, not changed:** the content script is injected at `document_idle`. In one run the Turnstile page was still `loading` after 14 s, nothing was reported and the source ended with `timeout after 15000ms` instead of `captcha`. Reporting `isBlockedUrl` from the background on `tabs.onUpdated` would cover it for every engine that has one; it touches shared code and was not done.
- **Not checked:** a signed-in page of a paid (not trial) plan, whose header and links may differ; whether a signed-in worker tab of the extension is ever sent to `/turnstile` (one typed address in a normal tab was not); where the signed-out allowance ends and what Kagi shows then; whether the Turnstile check passes by itself in the minimized worker window of the user's own headed browser.
- Checked in the user's running extension on 2026-11-13: the options page lists Kagi in the web group with its switch off and the running manifest has the four content-script patterns, for the first build. The final Kagi build (`origin/master` 470eccc) was activated there on 2026-11-14 together with the Google change (see [testing.md](testing.md)): Kagi is still off and no Kagi search was made, so the extension has not been run against Kagi in that browser.

## News search

News is a query-driven mode, not a headlines homepage. It reuses the existing `google`, `bravesearch`, `brave` and `exa` source IDs, credentials, defaults and marks. Bing and SearXNG do not declare news support in this release: Bing's news page redirected to the China homepage during verification, and SearXNG depends on the user's enabled upstream engines and instance settings.

- **Google (browser):** `/search?tbm=nws` returns article cards whose title is `[role="heading"][aria-level="3"]` inside the article link, including individual stories inside topic clusters. `.MgUUmf span` contains the publisher, `.UqSP2b` the excerpt, and `[data-ts]` the Unix article timestamp alongside the displayed age. The timestamp takes precedence over its rounded relative label; the label is retained in `news.timeText`. Explicit update labels produce `news.updatedAt`, never `publishedAt`. Raster thumbnails are embedded data URLs on the observed page; the image helper permits bounded PNG/JPEG/WebP/GIF data and HTTP(S), but excludes SVG/script/blob URLs. The links were Google's `/goto` wrappers, so the existing resolver remains responsible for finding the article URLs. Its final deduplication uses normalized URLs for news, preserving different article URLs that contain the same DOI/arXiv identifier. The live Tools links expose `tbs=qdr:d`, `qdr:w`, `qdr:m` for day/week/month, and `sbd:1` for date sorting; combined filters use a comma. Kiwi still applies its own time filtering after fusion.
- **Brave (browser):** `/news?q=…&source=news`, `.snippet[data-type="news"]`, with `.title`, `.generic-snippet .description`, `.site-name-content > span`, `.age-snippet` (or `.age-header`) and `a.thumbnail img`. Related web/AI cards are excluded. The timestamp is only a page-age label; because Brave's age can refer to publication or modification, it is retained with `timeKind: 'unknown'` and no `publishedAt`. Such results remain available in the any-time view but do not satisfy a strict publication-date range. No native date filter was exposed by the observed News filter panel, so the browser adapter does not invent one. Date ordering is applied by Kiwi after fusion.
- **Brave API:** news requests use `/res/v1/news/search`, the same subscription token, and top-level `results` rather than `web.results`. `freshness=pd/pw/pm` is supplied for day/week/month; the API's month is 31 days, while Kiwi's strict window is 30 days. `profile.name` and `thumbnail.src` supply publisher and thumbnail. `age`/`page_age` remain unknown-time text: the official definition of `page_age` permits published **or** modified dates, and `page_fetched` is retrieval time, not publication. The requested native freshness range therefore cannot establish a strict publication date by itself. See the [official News API](https://api-dashboard.search.brave.com/api-reference/news/news_search/get).
- **Exa API:** the existing `/search` request adds `category: 'news'` and, for a bounded range, `startPublishedDate` in ISO 8601. `publishedDate` is parsed conservatively (date-only remains date-only), `author` becomes `news.byline` and `meta.author`, and `image` supplies the thumbnail. It deliberately does not write `meta.authors`, which would cause a news article to be treated as a paper by deduplication. Existing Markdown snippet cleanup is reused. `contents.maxAgeHours` would control fetch freshness, not publication age, and is not substituted for a date filter. See [Search](https://exa.ai/docs/reference/search) and [content freshness](https://exa.ai/docs/search/quickstart).

Checked on 2026-11-13: in the user's headed Chromium, English `artificial intelligence` returned 13 Google article cards (including a topic cluster) and 50 Brave news cards. `google-news.html` preserves Google's result area and `bravesearch-news.html` the first 12 Brave cards; scripts/style elements/SVG and tracking attributes were removed, and Google's `gsessionid` redacted. The compiled parser was also run on live Chinese `人工智能`: Google with day+date filters returned 10 articles, all with publisher, thumbnail and timestamps within the previous 24 hours, in descending timestamp order; Brave returned 21 articles with publishers, 15 with thumbnails and some missing age labels. Google returned 10 despite `num=20`, so result count is a request, not a guarantee. Both the plain Bing News URL and one with `setmkt=en-US&setlang=en-US&cc=US` ended at `https://cn.bing.com/`, hence no Bing News parser was shipped. The dedicated parser/API contract tests and existing Google/API/parser regressions passed; API news fixtures are explicitly hand-written from the provider documentation, not live authenticated responses. Not checked here: authenticated Brave/Exa news responses, all source regions/layouts, and full worker-tab/extension behavior (record any later end-to-end verification separately).

## Adding a source

Adding a source touches five places: the hand-written `SourceId` union in `types.ts`, the `SOURCES` registry (typed as `Record<SourceId, …>`, so TypeScript flags a gap), its name, blurb and hover name in the message catalog (`source.label.<id>` and `source.blurb.<id>` in `catalog/options.ts`, `mark.<id>` in `catalog/newtab.ts`: typed dynamic keys, so TypeScript flags a gap) and `SOURCE_MARKS` in `lib/sourceMarks.ts` (also a `Record<SourceId, …>`; its logo goes into `assets/engine-logos`, see [newtab-page.md](newtab-page.md)), and `DEFAULT_CONFIG.sources` in `config.ts`. That last field is `Partial`, so a missing entry is not flagged; the source then silently defaults to disabled.

Later end-to-end checks on 2026-11-13: the original Chromium extension returned Google/Brave news (10 each), and Google day+date returned 10 in-range descending timestamps after the pipeline judge. Google `/goto` wrappers remained when the existing resolver could not reach a direct link. ## Shopping search (2026-11-13)

`shopping` uses three browser sources in `engines/shopping.ts`: Taobao (`s.taobao.com/search?q=…`), JD (`search.jd.com/Search?keyword=…&enc=utf-8`) and Amazon US (`www.amazon.com/s?k=…`). Each declares only shopping support and uses the existing user browser/session; none needs an API key. The result's optional `product` object holds thumbnail, displayed price, shop, sales text and rating. Price/currency/conditions remain source text, missing prices stay missing, and shopping skips the text judge and AI overview.

Product URLs are restricted to official product hosts and product paths. Taobao retains the numeric item ID and optional numeric `skuId`, including Tmall items returned by Taobao; JD retains its numeric item URL. Amazon retains the ASIN and any explicit `smid`/`offerListingID` seller/offer parameters (bounded lengths), because another offer may have a different price. Other search/session tracking parameters are discarded. Cards are deduplicated by these URLs, never by similar product titles. Thumbnail URLs accept only HTTP(S), without credentials or nonstandard ports. Ratings and sales are not inferred from one another.

- **Amazon:** has a 60-second minimum working timeout because cold minimized pages were still streaming without product cards after 36.5 seconds; a longer user timeout is retained, and cancellation remains immediate. It reads `[data-component-type="s-search-result"][data-asin]`, the product `h2` link, `img.s-image`, and the accessible `.a-price:not(.a-text-price) .a-offscreen` price exactly once. A crossed-out list price is not substituted when the current price is absent. The optional title differentiator is the snippet. Rating and monthly purchase text come from the reviews block. The user's delivery region can change the currency even on amazon.com; the observed page displayed GBP, which is kept rather than relabeled USD.
- **Taobao:** reads the current frontend's `doubleCardWrapperAdapt--` / `listCardWrapper--` cards with title, main-picture, price-part, shop-name and real-sales class prefixes. Selectors were derived from the site's public `pc-search-2024/1.8.61/js/main.js` bundle (CSS modules 60012, 35237, 49635, 18612, 20230). Price qualifiers such as a coupon condition are retained. The initial page without products showed `.J_MIDDLEWARE_FRAME_WIDGET` and `#baxia-dialog-content` login iframes at the unchanged search URL; those are login-wall signals, while the ordinary header sign-in link is not.
- **JD:** reads traditional `#J_goodsList .gl-item` product cards, `.p-name`, `.p-price strong`, `.p-shop`, and lazy-loaded `.p-img` URLs. `.p-commit` is a review count and is not emitted as sales or a star rating. The real signed-out request redirected to `passport.jd.com/new/login.aspx`, with `#formlogin`/`#smslogin`; the content-script matches include that login host.

Checked on 2026-11-13: the original headed Chromium rendered 48 Amazon coffee-grinder products. `amazon.html` is the first eight real rendered cards, with scripts/styles/SVG/forms, tracking attributes and query strings removed. `amazon-wireless.html` adds the first eight wireless-headphone cards from the actual minimized extension worker; evaluating the bundled parser on that live page returned all 16 product cards, with GBP prices and ratings. `taobao-blocked.html` and `jd-blocked.html` are real login-wall captures with iframe query data, inputs and other sensitive/session data removed. `taobao.html` is explicitly hand-written from the public frontend bundle; `jd.html` is explicitly hand-written against the traditional markup. Later, the same original worker successfully rendered Taobao products without any login/settings changes by the agent. `taobao-live.html` captures ten direct product cards and a preceding sponsored redirect card, which the parser excludes. Nested shop anchors are flattened to spans solely to preserve the live React DOM hierarchy when reparsed as HTML. Prices (including discount conditions), shops, sales text and images are preserved. The primary `img[class*="mainImg--"]` appears before a later `mainPic--` duplicate; extraction now accepts both, fixing thumbnails missing from an early result snapshot. This establishes actual successful product extraction, without claiming a particular login identity. Dedicated parser tests cover extraction, source currency, missing and crossed-out prices, price qualifiers, SKU/offer identity, safe URLs, duplicate and out-of-list cards, and actual login walls. No profile/config was changed during these source probes; only the probe's own new tabs were closed.

Not checked here: successful signed-in JD extraction, every Taobao/Amazon region/layout, and live captcha completion.
