## 一句话

Kiwi Search 是一个在用户自己的浏览器里跑的元搜索：用你自己的浏览器、登录状态和 Key，同时查多个来源，去重融合，用决策模型过滤内容农场，再用你自己的模型写出带引用的概览；同一套能力通过本地 MCP 服务提供给 Agent。没有 Kiwi 的服务器，不提供账号、Key 或代理。

## 工作标签组修复（Issue #9，2026-11-17）

## 关键决定和原因

1. **只在用户自己的浏览器里执行，不提供账号、Key 或服务器。** 服务端直接请求搜索引擎会进反爬页面，而用户自己的浏览器本来就能正常打开；这也让合规边界清楚：每次搜索由用户或用户自己的 Agent 发起，结果只给本人看。搜索引擎的服务条款通常禁止自动化查询，这些措施不等于对方授权，README 里写明了。
2. **不自动破解验证码，不打扰用户。** 遇到验证码只在页面上提示，用户点才弹窗；工作标签页放在一个最小化的专用窗口里，不进用户正在用的窗口。
3. **决策模型是可换服务商的一层。** 专用小模型又快又便宜，是推荐；聊天模型只作兜底。TypeSafe 的 Jev 只是预设，任何实现协议的服务都能接。
4. **概览和过滤只用于文字类模式。** 图片、视频、购物、小红书笔记、X 推文是媒体、商品或社交卡片，不判定、不概览。知乎和小红书不抓正文（登录墙），只用它们自己的摘录。
5. **论文必须在索引里核对存在才显示。** 智能学术里模型凭记忆点名的论文，查不到就丢掉，所以不会把编出来的论文放上页面。
6. **页面上不用文字展示搜索来源，只用小图标。** 每条结果在站点名后带返回它的引擎的真品牌 logo：多个引擎收录的叠成一叠、清晰；只有一个引擎的也画，但压到不透明度 0.5（2026-11-12 用户要求，原来是单个引擎的不画）。除此之外，只在验证码提示里提到来源。
7. **没有改默认搜索引擎的设置覆盖。** Chrome 不允许扩展自动改，README 里是手动添加的步骤。
8. **屏蔽列表默认全关，推荐名单里没有 eallion 的合集。** 订阅是向第三方主机发请求，要用户自己打开；那个合集混着作者的个人口味（整个 baidu.com、csdn.net 都在里面），想用的人可以自己按地址订阅。
9. **被屏蔽的结果折叠而不是删除。** 第三方名单和模型都会误判，一次点击能看到被藏的，才能发现和纠正。

## 待决定

- **上架各商店。** 2026-11-12 评估过：合适的顺序是 Edge → Firefox → Chrome → Safari。当时的最大障碍是 Chrome 单一用途规则：提供网页搜索体验的新标签页扩展要用 Chrome Search API 或 `chrome_settings_overrides.search_provider`。2026-11-14 起扩展不再覆盖新标签页，也不改任何搜索设置，界面放在网站 kiwi.moe 和扩展自带的页面两处（见 [web-app.md](internals/web-app.md)），这一项不再适用。还没做的：隐私政策页、收窄 `<all_urls>` 和 `tabs`、MCP 桥默认关闭、给审核员的说明、各商店的清单和打包。
- **摘要模型、默认开哪些来源、是否彻底移除 LLM 重排**：见 [PLAN.md](PLAN.md) 第 9 节。

## 接下来建议

**长期方向：设备间 P2P 同步**

目标：用户在自己的多台设备之间同步设置，不经过 Kiwi 的服务器。这是项目原则的延伸：用户完全控制自己的数据，Kiwi 尽可能不提供服务器。这一项只有方向，还没有设计，下面是立项时要先回答的问题。

| 问题 | 要点 |
|---|---|
| 同步什么 | 候选：来源开关与偏好、屏蔽列表和订阅、站点偏好、近期查询。API Key 和 MCP 配对凭据都在 `config` 和 `bridge` 里，默认不同步，要同步必须由用户单独确认。浏览器里的登录状态不属于 Kiwi，不同步 |
| 设备怎么找到彼此 | 没有 Kiwi 服务器，就得靠用户手动配对（二维码或配对码）或局域网直连。常见的 WebRTC 做法需要信令和 STUN，那是第三方或用户自备的服务，要先决定能不能接受，以及能否让用户自己指定 |
| 加密与信任 | 端到端加密，配对时建立密钥；传输内容只有已配对的设备能读，丢失或撤销某台设备时能让它失效 |
| 两台设备不同时在线 | 纯 P2P 做不到随时同步。需要决定：只在两台都在线时同步，还是再加一个由用户自己保管的加密导出/导入文件。浏览器自带的同步（`chrome.storage.sync`，用的是用户自己的浏览器账号，不是 Kiwi 的服务器）目前没有使用，可以作为对照方案评估 |
| 冲突 | 两台设备都改了设置怎么合并；要和 `config.ts` 的版本与迁移配合，旧版本设备不能把新字段冲掉 |
| 扩展里能不能跑 | 需要验证 MV3 的 service worker 能否做 WebRTC（我的理解是不能，要放到离线文档或页面里），以及 Chrome、Edge、Firefox 的差别。手机版和 Safari 等有了评估再说 |

**参照 Brave 同步的调查（2026-11-15，只读了文档，没做原型）。** Brave 的做法是：不需要账号；第一台设备生成 32 字节随机种子，用 BIP39 编码成助记词，新设备输入助记词或扫二维码加入同一条“同步链”；种子经 HKDF 派生出签名密钥用于向服务器认证，助记词经 scrypt 拉伸后作为 AES-CTR-HMAC 密钥，所有数据在本地加密。**但 Brave 并不是 P2P**：数据是加密后存放在 Brave 自己运营的服务器上（AWS，服务端代码是开源的 `brave/go-sync`），设备不需要同时在线。服务器看不到内容，但看得到设备名称和类型、条目的不透明 ID、版本和创建时间；12 个月无人访问的同步链会被删除；种子丢了谁也恢复不了。

所以能照搬的是“身份与加密层”，照搬不了的是“服务器”：

- **能照搬**：无账号；首台设备生成随机种子，助记词或二维码配对；端到端加密，没有 Kiwi 就读不到数据。这些都在本地完成。种子本身是 256 位随机数，不需要像用户口令那样拉伸，用浏览器自带的 WebCrypto（HKDF 派生密钥加 AES-GCM）即可，不用引入新依赖。这是我的设计判断，还没验证。
- **照搬不了**：Brave 的服务器。`go-sync` 说的是 Chromium 的同步协议，扩展用不上；而 Kiwi 的原则是不提供服务器。所以需要换一种“传输”，并且传输要和加密层分开，随时可换：
  1. **纯 P2P（WebRTC）**：不要任何服务器，但两台设备要同时在线，握手要靠手动交换配对码或局域网。Chrome 的离线文档有 `WEB_RTC` 这个理由，可以承载 WebRTC，生命周期没有限制，每个扩展同时只能开一个；service worker 本身能否用 WebRTC，官方文档没写，需要实测。
  2. **用户自己的浏览器同步**：把加密后的数据放进 `chrome.storage.sync`，由用户的 Google、Microsoft 或 Firefox 账号搬运。不是 Kiwi 的服务器，设备不用同时在线，但总量只有约 100 KB（单项 8 KB、最多 512 项、每分钟 120 次写入），只适合设置，装不下历史；只能在同一家浏览器之间同步（Chrome 与 Firefox 之间不行）。Edge 和 Firefox 上这个接口的表现还没核实。
  3. **用户自备的存储**：例如 WebDAV 或 S3 兼容存储，或同步文件夹里的加密文件。完全由用户掌控，但门槛高，放在后面。
  4. **Kiwi 自己运营中继**：最像 Brave，但和项目原则冲突，除非你以后改变主意，否则不考虑。
- **和 Brave 一样会有的限制**：种子丢了无法找回；配对后的设备都持有同一把密钥，移除某台设备不能让它读不了此后的数据，除非换种子（Brave 的文档里没有提到密钥轮换，我没有核实它的做法）。

**已决定（2026-11-15）：传输用 WebRTC 纯 P2P。** 身份与加密层仍按上面照 Brave 的做法（随机种子、助记词或二维码配对、端到端加密），传输层只用 WebRTC，不用浏览器自带同步，也不运营中继。因此：

- **两台设备要同时在线才能同步**，这是和 Brave 最大的区别。可以接受的体验是：设备上线后自动对上并补齐差异，而不是实时推送。
- **有三个必须先答的问题：**
  1. 握手信息怎么交换。第一次配对可以靠二维码或配对码，没有问题；但之后每次重新连接也要交换握手信息，如果每次都要用户手动操作，几乎没人会用。常见做法是借用公共的信令中继（Nostr、MQTT、BitTorrent tracker 之类）：握手信息先加密再放上去，中继只看到密文，数据本身仍是设备直连。已有的开源库 Trystero 就是这样做的，它的文档写明握手信息用 AES-256-GCM 加密、身份用 ECDSA 密钥并与 DTLS 指纹核对；但它的文档没有提扩展环境，也没有写默认的 STUN，要自己读源码或实测。这依然是第三方的基础设施，只是不是 Kiwi 的、也读不到内容；要不要接受、能不能让用户自己指定，由你决定。不接受的话，就只剩每次手动配对和局域网发现。
  2. 穿透 NAT。跨网络直连一般需要 STUN，常见公共 STUN 也是第三方服务；没有 STUN 时只有同一局域网内能连。严格的网络还需要 TURN 转发，但那就等于要有中继了。
  3. 扩展里能不能跑。Chrome 和 Edge 的 MV3 要把 WebRTC 放在离线文档里，靠 `runtime` 消息和 service worker 通信；Firefox 的 MV2 背景页可以直接用。这些都没有实测。
- **同步范围可以比浏览器自带同步放得开**：没有 100 KB 的限制，但仍然默认不同步 API Key 和 MCP 配对凭据。

先做：
1. 按 AGENTS.md 的规则，新建 `docs/internals/device-sync.md` 写设计和取舍（同步范围、威胁模型、配对方式、上面三个问题的结论），并在文档地图里加一行。
2. 先做一个验证用的小实验，不并入产品：Chrome 离线文档里建 WebRTC 连接，两台设备在同一局域网和不同网络下各试一次，记下什么情况能连上、什么情况连不上。
3. 实验结论出来、你对第 1 个问题定了之后，再做最小原型：两台桌面浏览器配对，只同步不含 Key 的设置。
