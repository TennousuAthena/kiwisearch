## 1. 定位与合规

做浏览器插件的原因：服务端直接请求搜索引擎会进反爬页面，而用户自己的浏览器本来就能正常打开这些页面。插件替用户打开各家结果页，把页面上的结果读出来，再合并、过滤、总结。

合规边界：
1. **只在用户自己的浏览器里执行。** 每次搜索都由用户（或用户自己的 Agent）主动发起，结果只给用户本人看，不转发，也不做成服务。
2. **遇到验证码不自动破解。** 把那个页面切到前台，让用户自己完成验证。
3. **频率接近真人。** 每个引擎单独限速、请求排队，单个引擎失败也不影响其他引擎。
4. **照常带用户自己的 Cookie 和登录状态**，不伪造请求头。

各家搜索引擎的服务条款一般都禁止自动化查询。以上几条能把个人使用的风险压得很低，但不等于对方授权。README 里写明了这一点。

## 2. 搜索模式与来源

每个来源自己声明支持哪些模式（`SearchSource.modes`），管线只查询支持当前模式的来源。

| 模式 | 来源 | 说明 |
|---|---|---|
| 网页 | Google、Bing、DuckDuckGo、Brave 网页方式、Yandex、百度（浏览器渲染；百度默认关，排在最后，在设置里开启要先确认）；Brave、Exa、DeepSeek Search、SearXNG（API） | Brave 网页方式不要 Key，见 P20 |
| 图片 | Bing 图片（浏览器渲染）、Openverse（API，免费，自带授权信息） | 不生成摘要、不做 Jev 判定 |
| 视频 | YouTube、哔哩哔哩、抖音（浏览器渲染，抖音默认关） | 不生成摘要、不做 Jev 判定；同一个视频的 youtu.be / Shorts / 分 P 链接按视频 ID 归并 |
| 知乎 | 知乎（浏览器渲染，需登录） | 走 Jev 过滤和 AI 概览，只用结果卡片里的摘录，不抓正文（登录墙）；同一问题下的不同回答不会被当成同一篇论文合并 |
| 小红书 | RedNote（rednote.com，默认开）、小红书国内站（xiaohongshu.com，默认关）；浏览器渲染，需登录 | 笔记卡片墙；不摘要、不判定；两个站的同一条笔记按笔记 ID 合并；链接保留打开笔记所需的 `xsec_token` |
| 公众号 | 搜狗微信（weixin.sogou.com，浏览器渲染，不需登录）；搜狗网页搜索作为“全部”的可选来源，默认关 | 找微信公众号文章（普通搜索引擎基本搜不到）；走 Jev 过滤和 AI 概览，只用搜狗给的摘录；链接是搜狗的中转链接，不带 Referer 打开能跳到 mp.weixin.qq.com |
| X | X（x.com，浏览器渲染，需登录） | 推文列表（作者、时间、正文、回复/转发/喜欢/浏览数、配图）；不摘要、不判定；只在用户打开“X”标签时搜索，不参与“全部”的自动选源；每次请求间隔至少 10 秒；长文只用标题和预览 |
| 学术 | Google Scholar（浏览器渲染）；OpenAlex、Crossref、arXiv、PubMed、Europe PMC、DBLP（API，免费，无需 Key）；百度学术、知网、Web of Science（浏览器渲染，只返回用户自己的浏览器会话能看到的内容） | 按 DOI / arXiv ID / 标题加年份去重（DOI 相同即同一篇：PubMed 和 Europe PMC 链接自己的页面，靠这条与 OpenAlex、Crossref 合并）；摘要用文献综述式提示词。默认只开 PubMed，其余新增来源由用户自己打开 |

同一个浏览器引擎的不同模式共用一个工作标签页和同一条限速队列，因为搜索引擎的风控按站点计算。

Openverse 匿名访问有限额（每页 ≤ 20 条、每分钟 20 次、每天 200 次），靠来源缓存摊薄。

## 3. 怎么在浏览器里打开结果页

所有工作标签页放在一个专用的窗口里，创建后立刻最小化，不占用用户正在用的窗口（要在创建之后再显式最小化一次，macOS 的 Chromium 会忽略创建时的 `minimized`）；每个来源固定一个标签页，闲置超过 N 分钟回收；窗口被用户关掉会自动重建；不使用无痕窗口。遇到验证码默认不弹窗：只在搜索页上提示，用户点“去验证”才把窗口调出来，验证完再最小化（设置里可以改成自动弹出）。窗口里的工作标签页放进同一个标题为“Kiwi Search”的灰色标签组（需要 `tabs` 和 `tabGroups` 权限）；不折叠，因为窗口里只有这一个组，折叠含活动标签页的组在 Chrome 里有边界情况，而且最小化的窗口本来就没人看；用户把标签页拖出组，或把组拆掉时，状态校验会把它当成用户的标签页放手，或把剩下的重新编组。

内容脚本现在按 `readySelector` 判断页面是否开始渲染结果，再提取；拿够请求条数立即返回，不够就等页面安静 600ms 后取现有结果，超时（12 秒）也取现有结果而不是返回空。

## 4. 架构与流程

```
apps/extension       WXT + React，Manifest V3（Chrome/Edge）
  newtab             搜索页：模式标签、AI 概览、结果列表 / 图片网格 / 论文列表
  options            来源开关与 Key、屏蔽与偏好（含屏蔽列表）、AI 模型、决策模型、重排、MCP 桥
  background         调度器（队列、限速、超时）、MCP 桥客户端、来源缓存、屏蔽列表的下载与更新
  content            各引擎的 DOM 提取
packages/core        与浏览器无关的纯逻辑：来源、去重与融合、决策模型判定、屏蔽列表、重排、摘要
packages/mcp         stdio MCP Server：BridgeSession 在 hub / relay 之间自动切换
```

处理流程（`runSearch`）：
1. 按模式挑选可用来源，并行查询。每个来源有自己的超时：浏览器来源从真正开始加载页面时才计时，排队时间不算。
2. 来源返回一个就推送一次部分结果。可选软截止时间（界面用 6 秒，MCP 不设）：到点后只要已有结果就先出首屏，慢的来源之后合并进来。
3. URL 归一化后去重（去跟踪参数；arXiv、DOI 合并，出版社页面里的 DOI 也算；论文再按“长标题 + 年份相容 + 都带学术元数据”合并；图片按图片文件本身去重）。
4. RRF 融合，每个来源的权重可调。
5. 域名规则：屏蔽的网站隐藏，优先的网站上移；屏蔽列表（订阅的和自己写的，见 P18）命中的结果同样折叠，并写明是哪个列表。不需要任何 Key。
6. Jev 判定（见第 5 节）；未启用时可选 Jina / Cohere / LLM 重排。
7. 取前几条未被隐藏的结果，读取正文；启用 Jev 时先检查正文有没有针对摘要模型的指令，有则不使用该页正文。
8. LLM 流式生成摘要，带 [n] 引用。提示词把来源声明为不可信数据。
9. 晚到的结果（被验证码拦住的来源，或超过软截止时间的来源）依次合并进来，启用 Jev 时同样先判定再合并。

**按意图选源（“全部”模式）**：配置了 Jev Key 时，通用来源立刻开始搜索，同时用一个只带搜索词的 Jev 请求（三个是非题：是不是学术问题、要不要搜知乎、要不要搜小红书）判断要不要加源。概率 ≥ 0.6 的路线，在这次搜索进行到一半时启动对应来源（按它自己的模式、数量和缓存），结果并入同一份融合排序；列表里知乎回答、小红书笔记、论文各自保持原来的卡片样子。没有 Key、出错、超过 3 秒、判定晚于软截止时间，就只用通用来源；指定了来源或不在“全部”模式时不做。

按来源、模式和查询词缓存 5 分钟，界面和 MCP 共用。Ollama 等本地模型不需要 Key 也能摘要。

## 5. 结果过滤（TypeSafe Jev）

> 这一节写的是用 Jev 做决策模型时的做法。P17 之后 Jev 只是预设之一，提供方可以换（专用服务或用户自己的聊天模型），见 [DECISION-PROVIDERS.md](DECISION-PROVIDERS.md)；下面的阈值和策略对所有提供方都一样，只有“每条结果一个请求”是专用服务的做法，聊天模型十条一批。

- **每条结果一个请求**（并发 10，遇到 429 / 529 重试一次，整体最长等 6 秒，超时后用已返回的判定），请求 `POST https://api.typesafe.ai/v1/systemone`。状态里放查询词和这一条结果（标题、地址、摘要、日期、正文摘录）。
- 问题：
  - 相关度（Score，四档：无关、沾边、部分满足、直接给出）；
  - 是否内容农场 / 搬运 / 自动生成的水文（Noul）；
  - 用户写的每条自然语言规则各一个 Noul。
- 策略写在代码里：
  - 排序 = 相关度 × 0.75 + RRF 先验 × 0.25，疑似垃圾的再打折；
  - 垃圾概率或规则概率 ≥ 0.7 时隐藏，归一化相关度 < 0.2 时隐藏；
  - 模型再不喜欢，主列表也至少保留 3 条；
  - 被隐藏的结果折叠在页面底部，显示原因，一次点击即可展开。
- 启用时取代重排。失败（Key 错误、超时）时回退到 RRF 顺序，并在状态行提示。
- 隐私：开启并填入 Key 后，搜索词和每条结果的标题、网址、摘要会发给 api.typesafe.ai；Key 留空则不发送，只用域名规则。
- 成本：文档标价每百万输入 token 0.042 美元，输出免费；一次搜索约 30 个请求、几千 token，不到 0.001 美元。实际延迟待实测。

**与最初设想的差别**：最初打算“一页一个请求，用路径引用同一份状态里的多条结果”。文档只演示了“一对 query–候选一个请求”，没有说明多条结果的引用写法和每个请求的问题数上限，所以改成每条一个请求。token 总量差不多，只是 HTTP 调用多。

## 6. 前端

- 首页：居中字标、圆角搜索框、框下的模式标签，右上角一个设置图标。
- 结果页：顶部小字标 + 搜索框，下面是“全部 · 图片 · 学术”下划线标签；结果列约 42rem，与搜索框左对齐；每条结果是圆形网站图标、站点名、面包屑地址、20px 蓝色标题、14px 灰色摘要。
- **不用文字展示搜索来源**：没有来源徽章、来源状态芯片、分数条。与来源有关的只有站点名后的引擎小图标（P13）和遇到验证码时的一行提示和“前往验证”。
- AI 概览放在结果上方，完成后超过约 6 行就折叠，引用角标悬停显示标题。
- 状态行只写“N 条结果（x 秒）”；还有来源在加载时写“仍在加载更多结果…”；过滤失败时写原因。
- 图片：等高行网格，点击后右侧出现预览（原图加载失败回退缩略图，← → 切换，Esc 关闭）；窄屏变成底部抽屉。
- 视频：左边缩略图（带时长角标），右边标题和“平台 · 频道 · 播放量 · 发布时间”，再加描述片段；平台名来自结果链接，不是搜索来源，所以不违反“不展示来源”。
- 学术：作者 · 期刊 · 年份、摘要、PDF / DOI / 被引次数；可按“某年以来”筛选，可按被引次数排序。
- 地址栏用 `pushState`，浏览器后退回到上一个查询；URL 形如 `?q=…&m=images`。
- 保留 Kiwi 自己的字标和叶绿主色（2026-11-13 按用户选择更新），不用 Google 的四色 logo。颜色一律来自 `lib/base.css` 的令牌，深浅主题都满足 AA 对比度。

## 7. MCP

- 工具：`search(query, mode?, sources?, limit?)`、`answer(query, mode?, sources?)`、`list_sources()`；`mode` 取 `web`（默认）、`images`、`video`、`academic`、`zhihu`、`xiaohongshu`、`wechat`、`x`；`answer` 不支持 `images`、`video`、`xiaohongshu` 和 `x`（没有可总结的文本），会直接报错并提示改用 `search`。
- 学术结果带作者、年份、期刊、被引、PDF；图片结果带原图地址、尺寸、授权；视频结果带频道、时长、播放量、发布时间；被过滤的结果不进列表，只在 `structuredContent.hidden` 里给出原因（命中屏蔽列表时还带 `list`，即列表名）。
- `BridgeSession`：第一个进程成为 hub 并绑定 `127.0.0.1:17345`，其余作为 relay 接入；hub 进程退出时，relay 随机延迟后抢占端口接管，不再让每个请求都等满 150 秒超时。
- 请求与界面共用队列、限速和缓存；`answer` 在摘要提供方为 `chrome-builtin` 时不可用。

已知缺口：
- **概览语言的几处取舍。** ① 默认“跟随浏览器”取的是浏览器的首选语言，不是搜索词的语言：浏览器是英语的人搜中文也得到英文概览（用户的开发浏览器就是 `en-GB`），要跟搜索词走得选“自动”。这是用户要求的默认。② 提示词措辞靠真实对比定的，但只在开发用的一个模型上、每种 4 次，别的模型听不听话没测；模型仍可能不照做。③ Chrome 内置模型只接受英、日、西、德、法的输出，建会话时没有声明输出语言（文档说不声明不报错但建议声明，声明了不支持的语言会报 `NotSupportedError`），所以选别的语言时可能写成英语，设置页只是提醒。④ 智能学术的“检索理解”那一句、状态行等其他文字不在这个设置里，仍按各自的规则。⑤ MCP 的 `answer` 用同一个设置，没有单次调用指定语言的参数：浏览器是中文、Agent 用英文提问时也会得到中文概览。
- **Exa 摘要的几处取舍。** ① 没有用 Exa 的 `summary`（让 Exa 写简介）：它干净（10 条里 0 条带表格），但每次搜索多 4–5 秒、费用 $0.017 对 $0.007，会让 Exa 每次都晚于新标签页的 6 秒软截止；适合做成可选项，没做。② 摘要的好坏取决于启发式（块的分类、“正文至少 20 个汉字或 40 个字母”、菜单与内容列表的区分）；页面本身没有正文时只能退而读列表或表格，读出来是“项目：值”或一行行单元格，不好看但不是竖线。③ 摘要里页面自己的怪空格（“1987 年”“3 9年”）没处理。④ DeepSeek 的 `snippet` 没有 Key 无法检查是否带 Markdown；SearXNG 的 `content` 是纯文本。⑤ Exa 的深蓝 logo 在暗色模式下对比度很低（叠层里也是），这次没改。
- **Brave 网页方式的几处取舍。** ① 验证码出现在和结果页相同的地址，所以 `isBlockedUrl` 没有用，只靠页面上的 `.captcha-wrapper` 标记；这个标记来自真实抓取，但 Brave 会在什么条件下弹验证码没有数据：只见过冷启动的无头 Chromium 被拦，开发浏览器（有历史、有登录）没被拦，普通用户的新浏览器会不会常被拦不知道。② 默认开。每多一个默认开的浏览器引擎，就多一个工作标签页和一次请求；如果实际常被拦，应改成默认关。③ 摘要里的日期保持 Brave 写的样子（“31 March 2025 - …”，月份是英文），没有解析成 `publishedAt`。④ 支持网页与新闻模式；新闻页保留原始日期标签，无法确定是发表还是修改，因此限定发表时间时折叠为未知。图片、视频页没做。⑤ API 方式和网页方式同时开时，同一个结果在融合里算两次（排名会略偏向 Brave），没有做自动去重，设置页的说明里让用户开一个就够。
- **屏蔽列表的几处没验证或有取舍。** ① 每天一次的更新靠 6 小时一次的闹钟和 Service Worker 每次启动时的检查：`isDue` 有单元测试，闹钟本身没在真实浏览器里等过；只在 Chromium 里跑过，Firefox 没试。② 只读能和搜索结果对上的规则：页面元素规则（`##`）、`$script` 之类的资源选项会跳过；正则必须写出网站名、不能有 `(a+)+` 这类嵌套量词和反向引用、不能同时匹配几个无关网址（是启发式，不是证明），所以 Content Farm Terminator 里两条只描述网址形状的正则、eallion 合集里 70 多条 Pinterest / Amazon 单品正则没有启用。③ 推荐名单里没有 eallion 的 uBlacklist 合集：它混着作者自己的口味（整个 baidu.com、csdn.net、juejin.cn、amazon.com、sohu.com 都在里面），想用的人可以按地址订阅。④ 推荐名单的地址是 2026-11-12 抓取验证的，不归我们管，搬家后设置页会显示下载失败。⑤ 匹配用结果的 `url` 和 `host`：搜狗微信这类返回跳转链接的结果，路径和正则规则看不到真实地址，只有按站点的规则能命中。
- **Bing 图片解析器未对照真实页面。** Bing 拒绝非浏览器客户端，拿不到真实 HTML，测试夹具是按已知结构手写的（文件头已注明）。需要在真实 Chrome 里搜一次图片，必要时重新抓取夹具并修正 `engines/bing.ts`。
- **Semantic Scholar 没有接入。** 匿名额度是全球共享的，实测直接 429，等有 Key 再加。
- 内容脚本和标签渲染的新逻辑没有自动化测试，需要在真实 Chrome 里手测：多结果引擎、验证码流程、DuckDuckGo 这类客户端渲染页面。

- 融合和正文抓取里仍有 Google `/goto` 包装链接的专用判断（`isGoogleGotoUrl`），可以改成命中上的 `opaque` 标记。

- **学术来源的核实情况（2026-11-12，六个来源各不相同）：**
  - **PubMed：对照真实响应。** esearch（JSON）加 efetch（XML）都是真实抓取；夹具里去掉了每篇的参考文献列表。用 efetch 而不是 esummary，因为只有 XML 带摘要，一次搜索 2 个请求（无 Key 限 3 次/秒；限流时 NCBI 返回 200 加 `error` 字段，已当错误抛出）。`HitMeta` 没有 `pmid` 字段，没加；靠链接相同和 DOI 相同合并。
  - **Europe PMC：对照真实响应**（5 条 MED、4 条预印本）。PMC 来源和专利（`PAT`）记录没抓到样本，映射是通用的；开放获取 PDF 链接（`documentStyle: 'pdf'`）没有真实样本，测试里那条是手改的。
  - **DBLP：未验证，没有真实 JSON。** dblp.org、dblp.uni-trier.de、dblp.dagstuhl.de 对这台机器的所有请求都返回 Anubis 工作量证明挑战页（HTTP 202 的 HTML；curl 和浏览器 UA 一样，绕开代理也一样）。没有去解这个挑战。夹具 `dblp.json` 是按官方文档的结构手写的（文件里有 `_note`），书目内容凭记忆；真实挑战页存为 `dblp-challenge.html`，来源遇到它会报“需要机器人验证”而不是返回空结果。用户自己的浏览器会不会也被挑战，没验证；若会，这个来源对那些用户就一直报错。
  - **百度学术：结果页对照真实页面。** `/s?wd=` 会在页面内跳到 `/ndscholar/browse/search`，卡片是 `div.paper-wrap.result`（10 条，期刊 9、图书 1）。干净的无头 profile 冷启动同一个地址会得到“百度安全验证”点选验证码（`baiduxueshu-blocked.html`，真实），先打开首页再搜就出结果。验证码页和结果页地址相同，只能靠验证码库的 `BiocFacade.js` / `BiocCaptcha.css` 识别；`wappass.baidu.com` 的地址判断是照搬百度网页搜索的，xueshu 没遇到过。列表里没有 DOI，结果链接是百度学术自己的详情页（不是中转链接）。学位、专利、会议卡片的结构没见过。
  - **知网：只有验证码页是真实的。** 无头 profile 搜两次（含先开首页）都被重定向到 `kns.cnki.net/verify/home?captchaType=blockPuzzle`（滑块验证码），没有去解。结果表格的解析（`table.result-table-list`、`td.name / author / source / date / data / quote`）凭记忆手写，夹具 `cnki.html` 是手写的、记录是编造的；列表视图本身没有摘要。搜索地址只确认了会被送到验证码，没确认 `korder` 和 `kw` 参数被识别。
  - **Web of Science：只有“没有权限”这条路是真实的。** 无头 profile 打开 `webofscience.com/wos/woscc/basic-search` 被送到 `access.clarivate.com/login?app=wos&…`（邮箱登录加“机构登录”），夹具 `wos-blocked.html` 是真实的（去掉了脚本和客户端 IP）。登录页在另一个域名，所以它在引擎的 `matches` 里，`isBlockedUrl` 认这个域名，来源会立刻报“被拦”而不是等超时。有权限时的一切都没验证：搜索地址（`general-summary?query=TS=(…)`）、`app-record` 卡片和 `data-ta` 属性都是凭记忆写的，夹具 `wos.html` 是手写的；标题链接另外按 `/full-record/` 路径找，属性变了只会少字段。页面渲染慢，而内容脚本只给 12 秒。需要在有权限的浏览器里手测一次。
- **网站图标。** 原来用 Chrome 的 `_favicon` 接口，它只返回浏览器已经有的图标（访问过或加了书签的站点），其他站点一律给同一个占位地球（实测 GitHub、Stack Overflow、Wikipedia 和一个编造的域名返回的 646 字节图片完全相同），所以大多数结果没有图标。现在改为：浏览器已有的图标 → 站点自己的 `/favicon.ico` 和首页 `<link rel="icon">` → 字母徽标，结果按域名缓存在 `storage.local`。真实扩展里 25 条网页结果有 18 个显示了图标，其余 7 个是字母徽标，没有破图。已知限制：Stack Overflow（403）和 CSDN（521）对不带 cookie 的请求返回风控挑战页，拿不到图标，只能显示字母徽标；没有测过 Firefox（`_favicon` 是 Chrome 的接口，那一层会直接跳过）；没有给“向没访问过的站点请求图标”做开关，没有接第三方图标服务（那样每条结果的域名都会发给第三方）。
